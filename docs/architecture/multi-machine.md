# Multi-machine federation and remote transports

Read before editing `src-tauri/src/daemon/machines/`, `daemon/remote_transport_table.rs`, `daemon/methods/machines.rs`, `daemon/methods/spawn_chat/forward.rs`, `ipc/machines.rs`, `ipc/mirror.rs`, anything that reads `rpc::Transport` or `Instance.machine`, or the machine UI (`machine-field.ts`, `remote-access.ts`). Request paths and known limits: `docs/multi-machine.md`.

- **Multi-machine federation module map.** `src-tauri/src/daemon/machines/registry.rs` owns this daemon's identity plus its paired peers, persisted at `<app_data>/machines[suffix].json`. `peer_client.rs` is the HTTP client (`/api/health`, `/api/rpc`, `/api/pair`) for talking to one paired peer. `peer_link.rs` keeps one peer's `mirror.rs` cache entry current over that peer's `/api/global/stream` WS; `hub.rs` owns the set of live `peer_link` tasks, one per peer, resynced on every pairing mutation. `forward.rs` is the RPC-level forwarder for a call whose `session_id`/`id` resolves to a mirrored row; `relay.rs` is its chat-event-stream counterpart. **A second, deliberately separate forwarder lives at `daemon/methods/spawn_chat/forward.rs`** - `machines/forward.rs` keys on a `session_id` already known to be mirrored, while spawn_chat dispatches a brand-new spawn to an explicitly named `machine` argument before any session exists. Do not merge them. `iroh_dial.rs` is `peer_client::reach_url`'s fallback when a peer has no `direct_url`: dials its iroh id and exposes the tunnel as a local loopback proxy port. `peer_scope.rs` enforces each peer's "Can drive chats" switch on `/api/rpc` and the REST send route. Route a session id to a peer only through `machines::mirrored_owner` (local registry first), never `MirrorState::owner_of` directly, or a peer can claim a local chat's id. RPC methods (`list_machines`/`pair_machine`/`unpair_machine`/`set_machine_label`/`list_machine_projects`) live in `daemon/methods/machines.rs`; Tauri wrappers in `ipc/machines.rs`. `MirrorState` also holds a short-lived pending-owner map (`forward_start_session` records a freshly forwarded id so its first attach/send route before the peer's next `instances_changed`) and each peer's pending-prompt cache, refreshed by `peer_link` and merged into `list_pending_prompts` for every caller except a `PeerMachine` one. Clients send `session_id` alongside a prompt's `request_id`/`id` so answers forward. `hidden.rs` owns cross-machine hidden-chat state: the host machine owns a chat's flag, `update_hidden_chats` forwards a mirrored id to its host, and `MirrorState::hidden_sessions` mirrors each peer's list filtered by ownership. Request paths, the 2026-10-08 gap fixes, and known limits: `docs/multi-machine.md`. Frontend: `src/views/sessions/machine-field.ts` is the machine-chip picker in the new-chat project picker (desktop and phone); the Paired machines section (pairing form, peer list, self-label editor) lives in `src/views/settings/subviews/remote-access/remote-access.ts`.

- **`daemon/remote_transport_table.rs`'s `TRANSPORT_TABLE` replaced `SAFE_METHODS`.** It lived in `remote_handlers.rs` until todo 934 split it out; only `allowed` is still re-exported from there, so reach the table and `TransportMask` by their own module path. Each entry's `TransportMask` is `P` (phone only), `PM` (phone and a paired peer machine), or `M` (peer machine only); a method absent from the table is desktop-pipe only, refused for every remote transport. Every row needs a rationale comment, and every `machine: true` mask needs an entry in `allowlist_*`/`peer_machine_mask_is_phone_subset_or_a_named_machine_only_exception` - those tests moved with the table and live in `remote_transport_table.rs`'s own test module. A method that must work for a mirrored session needs to be `PM` or `M`, because `machines/forward.rs` only forwards a method `allowed()` accepts for `Transport::PeerMachine`.

- **`rpc::Transport` replaced the old `REMOTE_TRANSPORT: bool`.** It's `Local` (desktop pipe), `Phone`, or `PeerMachine(machine_id)`. `ConnectionContext::remote` is still `true` only for `Transport::Phone` - never trust a request payload's claimed machine identity, read `ctx.transport` instead (see `methods/machines.rs::peer_unpaired` and `methods/channel.rs::register_channel_rpc`, both of which derive the caller's machine id/label from `ctx.transport`, never from `params`).

- **`Instance.machine: Option<MachineRef>`** means the row is mirrored in from a paired peer (`None` = hosted on this daemon), stamped only by `daemon::machines::all_instances`/`MirrorState::instances`. `is_remote` still means "reached over remote (phone) transport" and the sidebar's "Remote" segment still means an external/automated session kind - none of the three (`machine`, `is_remote`, session kind) implies either of the others.

- **Mirroring loop guards.** `MirrorState::set_instances`/`instances` both drop any row that already carries a `machine` tag, so a peer's own mirrored copy of a THIRD machine is never re-mirrored (no chains past one hop). `machines/forward.rs::forward_one` and `spawn_chat_or_forward`/`post_message_or_forward` never forward when the request's own `ctx.transport`/the resolved peer is `PeerMachine` again - a call already arriving from a peer is always about this daemon's own local sessions.

- **Two daemons on one box for local testing:** `CC_DATA_DIR=<dir> CC_DAEMON_INSTANCE=<label> CC_REMOTE_PORT=<port>` (see `settings/paths.rs::resolve_data_dir`, `daemon/instance.rs`, `remote_server.rs`'s port resolution). Only the default instance (`instance_suffix()` empty) advertises an iroh tunnel (`iroh_tunnel.rs`), so pair two local instances by a direct `http://127.0.0.1:<port>` URL, not iroh. The in-process two-daemon fixture to copy for a new test is `machines/peer_link.rs::tests::two_daemons_mirror_each_other_over_loopback`, built on `remote_server::spawn_on`.

- **A main chat's sub on a paired machine** (home owns the family, host runs the process, git bundles carry the commits): `docs/cross-machine-subchats.md`.
