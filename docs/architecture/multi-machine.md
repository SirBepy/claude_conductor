# Multi-machine federation and remote transports

Read before editing `src-tauri/src/daemon/machines/`, `daemon/remote_transport_table.rs`, `daemon/methods/machines.rs`, `daemon/methods/spawn_chat/forward.rs`, `ipc/machines.rs`, `ipc/mirror.rs`, anything that reads `rpc::Transport` or `Instance.machine`, or the machine UI (`machine-field.ts`, `remote-access.ts`). Request paths and known limits: `docs/multi-machine.md`.

- **Multi-machine federation module map.** `src-tauri/src/daemon/machines/registry.rs` owns this daemon's identity plus its paired peers, persisted at `<app_data>/machines[suffix].json`. `peer_client.rs` is the HTTP client (`/api/health`, `/api/rpc`, `/api/pair`) for talking to one paired peer. `peer_link.rs` keeps one peer's `mirror.rs` cache entry current over that peer's `/api/global/stream` WS; `hub.rs` owns the set of live `peer_link` tasks, one per peer, resynced on every pairing mutation. `forward.rs` is the RPC-level forwarder for a call whose `session_id`/`id` resolves to a mirrored row; `relay.rs` is its chat-event-stream counterpart. **A second, deliberately separate forwarder lives at `daemon/methods/spawn_chat/forward.rs`** - `machines/forward.rs` keys on a `session_id` already known to be mirrored, while spawn_chat dispatches a brand-new spawn to an explicitly named `machine` argument before any session exists. Do not merge them. `iroh_dial.rs` is `peer_client::reach_url`'s fallback when a peer has no `direct_url`: dials its iroh id and exposes the tunnel as a local loopback proxy port. `peer_scope.rs` enforces each peer's "Can drive chats" switch on `/api/rpc` and the REST send route. Route a session id to a peer only through `machines::mirrored_owner` (local registry first), never `MirrorState::owner_of` directly, or a peer can claim a local chat's id. RPC methods (`list_machines`/`pair_machine`/`unpair_machine`/`set_machine_label`/`list_machine_projects`) live in `daemon/methods/machines.rs`; Tauri wrappers in `ipc/machines.rs`. `MirrorState` also holds a short-lived pending-owner map (`forward_start_session` records a freshly forwarded id so its first attach/send route before the peer's next `instances_changed`) and each peer's pending-prompt cache, refreshed by `peer_link` and merged into `list_pending_prompts` for every caller except a `PeerMachine` one. Clients send `session_id` alongside a prompt's `request_id`/`id` so answers forward. `hidden.rs` owns cross-machine hidden-chat state: the host machine owns a chat's flag, `update_hidden_chats` forwards a mirrored id to its host, and `MirrorState::hidden_sessions` mirrors each peer's list filtered by ownership. Request paths, the 2026-10-08 gap fixes, and known limits: `docs/multi-machine.md`. Frontend: `src/views/sessions/machine-field.ts` is the machine-chip picker in the new-chat project picker (desktop and phone); the Paired machines section (pairing form, peer list, self-label editor) lives in `src/views/settings/subviews/remote-access/remote-access.ts`.

- **`daemon/remote_transport_table.rs`'s `TRANSPORT_TABLE` replaced `SAFE_METHODS`.** It lived in `remote_handlers.rs` until todo 934 split it out; only `allowed` is still re-exported from there, so reach the table and `TransportMask` by their own module path. Each entry's `TransportMask` is `P` (phone only), `PM` (phone and a paired peer machine), or `M` (peer machine only); a method absent from the table is desktop-pipe only, refused for every remote transport. Every row needs a rationale comment, and every `machine: true` mask needs an entry in `allowlist_*`/`peer_machine_mask_is_phone_subset_or_a_named_machine_only_exception` - those tests moved with the table and live in `remote_transport_table/tests.rs`. A method that must work for a mirrored session needs to be `PM` or `M`, because `machines/forward.rs` only forwards a method `allowed()` accepts for `Transport::PeerMachine`.

- **`rpc::Transport` replaced the old `REMOTE_TRANSPORT: bool`.** It's `Local` (desktop pipe), `Phone`, or `PeerMachine(machine_id)`. `ConnectionContext::remote` is still `true` only for `Transport::Phone` - never trust a request payload's claimed machine identity, read `ctx.transport` instead (see `methods/machines.rs::peer_unpaired` and `methods/channel.rs::register_channel_rpc`, both of which derive the caller's machine id/label from `ctx.transport`, never from `params`).

- **`Instance.machine: Option<MachineRef>`** means the row is mirrored in from a paired peer (`None` = hosted on this daemon), stamped only by `daemon::machines::all_instances`/`MirrorState::instances`. `is_remote` still means "reached over remote (phone) transport" and the sidebar's "Remote" segment still means an external/automated session kind - none of the three (`machine`, `is_remote`, session kind) implies either of the others.

- **Mirroring loop guards.** `MirrorState::set_instances`/`instances` both drop any row that already carries a `machine` tag, so a peer's own mirrored copy of a THIRD machine is never re-mirrored (no chains past one hop). `machines/forward.rs::forward_one` and `spawn_chat_or_forward`/`post_message_or_forward` never forward when the request's own `ctx.transport`/the resolved peer is `PeerMachine` again - a call already arriving from a peer is always about this daemon's own local sessions.

- **Two daemons on one box for local testing:** `CC_DATA_DIR=<dir> CC_DAEMON_INSTANCE=<label> CC_REMOTE_PORT=<port>` (see `settings/paths.rs::resolve_data_dir`, `daemon/instance.rs`, `remote_server.rs`'s port resolution). Only the default instance (`instance_suffix()` empty) advertises an iroh tunnel (`iroh_tunnel.rs`), so pair two local instances by a direct `http://127.0.0.1:<port>` URL, not iroh. The in-process two-daemon fixture to copy for a new test is `machines/peer_link.rs::tests::two_daemons_mirror_each_other_over_loopback`, built on `remote_server::spawn_on`.

- **A main chat's sub on a paired machine** (home owns the family, host runs the process, git bundles carry the commits): `docs/cross-machine-subchats.md`.

- **A peer marked offline is asked before a caller is refused, and the caller waits a few seconds at most (2026-11-15).** `forward::require_online` runs `MachineHub::probe_offline_peer` (`machines/hub.rs`): one shared probe per peer, in its own task, bounded by `PROBE_BOUND` (35s, a cold iroh dial plus a health call). A caller waits for it only until the probe is `PROBE_WAIT` (4s) old and is then refused with "<label> is offline"; the probe runs on and marks a peer that answers late online. The wait is short on purpose: every request that names a sleeping peer (a mirrored row's project face, anything routed by a mirrored `session_id`) used to be held for the whole 30s dial, measured on the live daemon on 2026-11-15, which is past the phone's 15s read timeout, so the phone reported its link to this PC as down ("Waiting for your PC", "Reconnecting to your PC"). On the phone side `get_project_icon` / `get_project_tech` are `BACKGROUND_READS`, and a `p strip_show` journal line ends with what raised the strip (`method=<rpc>` or `cause=stream|requests|stream+requests`).

- **Settings and character-file sync between paired machines (2026-11-15).** The model is `settings/sync.rs`: `PERSONAL_KEYS` is an allowlist of `settings.json` keys (look and feel, update mode, whitelist) and `MACHINE_LOCAL_KEYS` names every other field with its reason; a key on neither list is not synced, and a test fails until a new `Settings` field is classified. Each personal key carries a stamp `{at, by}`, the last writer wins per key, and a stamp that is not a time or is over 5 minutes ahead is refused. **The app process owns the stamps and `settings.json`**: `settings/sync_store.rs` writes `settings-sync-clocks.json` beside it, `store::save` stamps every personal key a save changed (it diffs the file as it was against what was written, under one lock), and a peer's merge goes through `sync_store::apply_incoming`/`apply_to_live`, which writes the stamps it received and never a fresh one, so a merge is not a local edit and nothing loops. The daemon only moves changes: `machines/settings_sync.rs` handles the machine-only `settings_sync` RPC (refused unless the owner's per-peer "Sync settings" switch, `MachinesFile::sync_settings_peers`, is on for `ctx.transport`'s machine; every stamp's `by` is rewritten to that machine, only personal keys of at most 256 KB pass) and hands them to the app as `settings_sync_incoming`. What goes out is read from `settings.json` and the stamps file, stamps first (the app's pushed snapshot trails the disk, and a new stamp beside an old value would make a peer keep the old value for good): on every `set_settings` whose stamps changed (`on_app_push`), and as an exchange (send ours, ask for theirs, `want_reply`) when a peer link connects, when the switch is turned on, and on the app's first push of a boot. Nothing is queued on disk: the state travels, and an unreachable peer catches up on the next exchange; a change that reaches a daemon whose app is away is kept in memory and handed to the app after its next settings push. A key the receiving peer wrote itself is not sent back. `machines/asset_sync.rs` copies `<app-data>/characters/<game>/<character>/` from a syncing peer, gated by the same switch: pull-only, fills gaps only (never replaces or deletes), paths checked by `safe_rel` on both ends (media extensions only, no symlinks), `character.json` of a character last, one pull per peer at a time, 512 KB chunks over `character_assets_manifest`/`character_asset_chunk`; a finished pull invalidates the character cache in both processes. Machine-local settings (paths, ports, accounts, projects, session ids, chat-to-character picks, and `retention`: a peer's shorter setting would prune this machine's own SQLite history for good) never sync. The switch is flipped only over the desktop pipe (`set_machine_sync_settings`) and unpairing clears it.
- **Settings sync: trust is transitive, and other limits (2026-11-15 review).** With A-B and B-C switched on and A-C off, a change C makes still reaches A through B: each machine forwards every stamped personal key it holds, and `outgoing_for` only leaves out the keys the receiving peer wrote itself, so it filters the receiver, not the origin. Behavior kept on purpose: "Sync settings" says "this machine is mine" per link, not a closed group. Also true: a Settings page writes only the controls the user changed (`settings-save.ts` `pickEdit`, against the values the page showed when it mounted), so a page left open never reverts a peer's change; an absent key written as the value the UI already shows for it is not stamped (`sync::is_what_absent_means`); a local edit is stamped after the stamp it replaces (`local_stamp_time`), and a clock difference over 5 minutes, which makes a merge refuse the stamps, is logged once per peer, answered to the sender as `clock_skew` and shown on the machine's row (`PeerMachineView::settings_note`), never silently one-way; switching the switch off stops a running character pull at the next file or chunk and drops a late `want_reply` answer; a pulled `character.json` is confined to its own folder (`util::path::confine`); `retention` is machine-local; a second corrupt stamps file is kept under a timestamped `.bad` name.
