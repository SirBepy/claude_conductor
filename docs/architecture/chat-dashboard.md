# Chat dashboard (lane 1 and lane 4)

Read before editing `src/shared/chat/dashboard/`, `src/views/sessions/chat-dashboard/`, `chat-view-pref.ts`, the Settings > Chat defaults dashboard rows, or `daemon/methods/quick_views.rs`. Design: `docs/chat-dashboard-design.md`.

- **Chat dashboard (lane 1 of docs/chat-dashboard-design.md).** Settings > Chat defaults > Chat view (`chatView` in settings.json's extra map, absent = Dashboard; the phone always draws Messages) picks what a chat window shows. The command palette's "Toggle Dashboard / Messages" row (shortcut id `toggle-chat-view`, no default keys, registered desktop-only in `sessions-dom-wiring.ts`) flips that same app-wide setting through `toggleChatView` in `chat-view-pref.ts`; it is not per chat (Joe, 2026-11-13). The model is `src/shared/chat/dashboard/dashboard-model.ts`: pure, it derives every zone from `ChatRenderer.messages` (send_message cards, question cards, `report_turn_status` rows, Joe's own messages) plus `ChatRenderer.dashPlans` (every `write_plan` of the chat, which draws no row; `remapIndices` keeps each plan's `at` and `lastAt` aligned). **To add a card, add a derive function and one entry to `ZONES` there (column, order, derive returning null when empty), then its renderer in `src/views/sessions/chat-dashboard/dashboard-zones.ts`'s `ZONE_VIEWS`, which is typed against `ZoneId` so a zone with no renderer fails typecheck.** Never touch the transcript renderer for a card. `chat-dashboard.ts` mounts beside `.session-messages` from `wireRenderer`, re-derives on `ChatRenderer.onFlushed`, redraws only zones whose HTML changed, and moves the chat's real status line (`.session-thinking`) into the Plan card's status slot while that card is drawn. The transcript keeps rendering underneath, hidden by `.session-pane[data-chat-view="dashboard"]`, so Messages view is byte-for-byte today's. View-harness `mountView` pins `chatView: "messages"` unless a spec passes `chatView: "dashboard"`. **The Answers card is one of two zones with their own DOM** (`chat-dashboard/answers-card.ts`): its zone renders a fixed `.ax-host` and the card draws inside it, so a re-derive never wipes an animation or a thread's message box. Its data is `src/shared/chat/dashboard/answers-model.ts` (only `answer`/`rating` messages count, plus a sub's finish card that carries a `question`: `spawn_chat` and `subchat send` take one, the daemon moves it from the sub's brief onto its next finish card (`finish::commit_finish_at`), and that card is the answer, so a subchats main chat never relays one; `send_message`'s answer-only `question` field is Claude's rewrite of Joe's question, falling back to his message). Read marks, thread links and + questions are daemon-side per chat (`ask/answer_state.rs`, `<data>/ask/<sid>.answers.json`, RPCs in `daemon/methods/answers.rs`, desktop-pipe only); a thread is an Ask thread, so follow-ups run the Ask sidecar with no spawn path of their own. History is the command palette with `remember: false`, `match` and `decorate` (`PaletteSources` in `palette-ui.ts`). **The Subchats card is the other one** (`chat-dashboard/subs-card.ts`, fixed `.sx-host`): its rules (who is listed, the one-hour fold of finished subs under "+N earlier" which is display only and never closes a sub) are the pure `shared/chat/dashboard/subs-model.ts`, its items come from the instance list through `chat-dashboard/subs-source.ts` (not from the transcript), and `syncInstances` pings `ChatDashboard.onSessionsChanged`. The avatar's right-click menu is `buildSubCardItems` (`chat-menu-items.ts`) drawn by `sub-card-menu.ts`. **Pin to sidemenu replaced Move to sidebar in the chat menu:** `Instance.pinned_to_sidebar` (registry snapshot, `#[serde(default)]`) is set by the `set_sub_pinned` RPC and only makes `sidebar-entries.ts` list the sub; the sub stays a sub (the daemon's `move_sub_to_sidebar` RPC is left but nothing in the UI calls it). A sub's images and brief come from `list_session_images` (history_scan's `facts_for`, ids read through `dashboard_gallery_image`) and `get_sub_brief` in `daemon/methods/sub_view.rs`. **Every model battery takes the effort colour:** `modelBatteryHtml(model, effort)` sets `data-effort` and `effort-battery.css` colours it (high is the default grey); a new battery goes through that function.

- **Chat dashboard extras (lane 4).** Links and files, the Preview window and Changes are zones in the same `ZONES` table. Links and files is derived on render (no Links store): `shared/chat/dashboard/links-model.ts` scans send_message text, details and card rows for URLs and file paths, plus `pr_preview` drafts and the Edit/Write tools' `file_path`; it draws with links or files, or once the chat has a plan, because it hosts the three quick-view buttons (Bigger plan, Decided, Project memory). Those call the desktop-pipe-only `chat_quick_view` RPC (`daemon/methods/quick_views.rs`, IPC wrapper `ipc/quick_views.rs`): `<cwd>/.claude/todos/PLAN.md` (else a plan `.md` the chat names, opened as a file ref), the main chat's subchats decisions log (`decisions::read_log`, a sub reads its parent's), and the Auto Memory folder (the session transcript's sibling `memory/`, else the cwd encoded as Claude Code names it). `chat-dashboard/quick-view.ts` is the read-only dialog. The Preview window reads `list_previews` scoped to the chat's family (`scopeRoot`), refreshed on the `preview` event, and lists only the previews whose `session_id` is this chat (a sub read in place: the sub), newest as a big scaled iframe tile and the rest as a thumbnail strip; the family's other previews sit behind an "N more by other chats" fold grouped by owner (`derivePreviewWindow`). A question's figures are the `visuals` of the own message sent just before it (`figuresBefore`). **Optional zones:** `SECTION_DEFAULTS` in `dashboard-model.ts` (links on, preview on, changes off) and Joe's overrides in settings.json's extra map under `dashboardSections` (`chat-view-pref.ts` `readSections`), switched in Settings > Chat defaults; a new optional card adds its id there and one row in `DASHBOARD_SECTIONS` in `chat-defaults.ts`. Extras CSS is `chat-dashboard/dashboard-extras.css`.

- **From subs draws every sub report that is not an answer** (`reports` zone, `deriveReports` in `dashboard-model.ts`). The main chat is told never to relay a sub's card, so a job's finish (no `question`), the all-finished card and when-done's note have no other home on the dashboard: Answers takes only a finish carrying a question, Waiting only blockers, and the Subchats card only avatars (its verdict sits behind a click). Joe, 2026-11-13: "i dont see subchats answers in the main chat window". Each report is drawn by `cardHtml`, the very sub card Messages view draws, newest first, three shown and the rest under "N earlier" (`DashUi.reportsOpen`). It reads `DashboardInput.subCards` (`ChatRenderer.subCardPool`) as well as the rows, because the dashboard hides the transcript and its older pages never load, so a card older than the first page lives only in the pool. Answers reads only rows, so a finish carrying a question that has no loaded row is drawn here too. A tied timestamp puts the card written later (log order) first. Nothing is dismissed or marked read.

- **Waiting on you holds only blockers that still stand.** `ownBlockerLive` in `dashboard-model.ts` drops an own blocker once Joe writes, once the chat sends a later report, answer or plan, or once it sends a later blocker waiting on the same thing (`sameWait` over `blockerTargets`); relayed messages and question-card answers are not Joe writing, so without that a chat driven by another chat kept every blocker. Each card in Waiting on you and Waiting on <target> carries its written time and, on hover, an x (Clear all once two can go); removals are `DashboardInput.dismissed`, keyed by `waitingKey` and kept per chat in localStorage by `chat-dashboard/waiting-dismissed.ts`.
