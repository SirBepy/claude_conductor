# Chat dashboard (lane 1 and lane 4)

Read before editing `src/shared/chat/dashboard/`, `src/views/sessions/chat-dashboard/`, `chat-view-pref.ts`, the Settings > Chat defaults dashboard rows, or `daemon/methods/quick_views.rs`. Design: `docs/chat-dashboard-design.md`.

- **Chat dashboard (lane 1 of docs/chat-dashboard-design.md).** Settings > Chat defaults > Chat view (`chatView` in settings.json's extra map, absent = Dashboard; the phone always draws Messages) picks what a chat window shows. The command palette's "Toggle Dashboard / Messages" row (shortcut id `toggle-chat-view`, no default keys, registered desktop-only in `sessions-dom-wiring.ts`) flips that same app-wide setting through `toggleChatView` in `chat-view-pref.ts`; it is not per chat (Joe, 2026-11-13). The model is `src/shared/chat/dashboard/dashboard-model.ts`: pure, it derives every zone from `ChatRenderer.messages` (send_message cards, question cards, `report_turn_status` rows, Joe's own messages) plus `ChatRenderer.dashPlans` (every `write_plan` of the chat, which draws no row; `remapIndices` keeps each plan's `at` and `lastAt` aligned). **To add a card, add a derive function and one entry to `ZONES` there (column, order, derive returning null when empty), then its renderer in `src/views/sessions/chat-dashboard/dashboard-zones.ts`'s `ZONE_VIEWS`, which is typed against `ZoneId` so a zone with no renderer fails typecheck.** Never touch the transcript renderer for a card. `chat-dashboard.ts` mounts beside `.session-messages` from `wireRenderer`, re-derives on `ChatRenderer.onFlushed`, redraws only zones whose HTML changed, and moves the chat's real status line (`.session-thinking`) into the Plan card's status slot while that card is drawn. The transcript keeps rendering underneath, hidden by `.session-pane[data-chat-view="dashboard"]`, so Messages view is byte-for-byte today's. View-harness `mountView` pins `chatView: "messages"` unless a spec passes `chatView: "dashboard"`. **The Answers card is one of two zones with their own DOM** (`chat-dashboard/answers-card.ts`): its zone renders a fixed `.ax-host` and the card draws inside it, so a re-derive never wipes an animation or a thread's message box. Its data is `src/shared/chat/dashboard/answers-model.ts` (only `answer`/`rating` messages count, plus a sub's finish card that carries a `question`: `spawn_chat` and `subchat send` take one, the daemon moves it from the sub's brief onto its next finish card (`finish::commit_finish_at`), and that card is the answer, so a subchats main chat never relays one; `send_message`'s answer-only `question` field is Claude's rewrite of Joe's question, falling back to his message). Read marks, thread links and + questions are daemon-side per chat (`ask/answer_state.rs`, `<data>/ask/<sid>.answers.json`, RPCs in `daemon/methods/answers.rs`, desktop-pipe only); a thread is an Ask thread, so follow-ups run the Ask sidecar with no spawn path of their own. History is the command palette with `remember: false`, `match` and `decorate` (`PaletteSources` in `palette-ui.ts`). **The Subchats card is the other one** (`chat-dashboard/subs-card.ts`, fixed `.sx-host`, LEFT column order 26 right under Waiting on you): a stuck sub (asking, paused, limited, stopped) is a tinted `.sx-item` row with one `subWhy` line (five rows, then "+N more"), a working sub an avatar in the `.sx-row` strip, and a click opens that sub's mini dashboard as a `SubPeek` (`sub-peek.ts`), a `position: fixed` card Joe drags by its top line; several stay open at once and each owns its composer and gallery. **A queued sub (held behind another, `progress.waiting_for`) has no process, so it is never a stuck row or a strip avatar** (Joe, 2026-11-18): `cardCounts` in `subs-model.ts` counts it apart as "N queued" (a chip beside the "N working · N asking · N stuck or waiting" words, hidden at 0), and clicking the chip opens `sub-queued-popup.ts` (`QueuedPopup`, the app's `openAnchoredPopover`, rows in start order from `queuedSubs`, "Starts after X" or "Starts after N chats" from `startsAfterText`, footnote `QUEUED_FOOTNOTE`). The popup patches in place on every refresh (a row that starts folds away at its `transitionend`, neighbours slide by FLIP, the popup never replays its enter, an empty list closes it); a row click is the avatar's `toggle` (it opens the peek and closes the popup, focus is not pulled back), a row right-click is the same chat menu, and the task line is one cached `get_sub_brief` per id. Space on the chip or on a popup row stops propagation because the composer's stray-input relay would otherwise type it into the composer (the same relay catches Space on any other focused button). The count and popup styles are `chat-dashboard/sub-queued-popup.css`. The peek shows the current plan step only (hover data), not the full step list, which would need a daemon read of the sub's transcript plan. its rules (who is listed, the one-hour fold of finished subs under "+N earlier" which is display only and never closes a sub) are the pure `shared/chat/dashboard/subs-model.ts`, its items come from the instance list through `chat-dashboard/subs-source.ts` (not from the transcript), and `syncInstances` pings `ChatDashboard.onSessionsChanged`. The avatar's right-click menu is `buildSubCardItems` (`chat-menu-items.ts`) drawn by `sub-card-menu.ts`. **Pin to sidemenu replaced Move to sidebar in the chat menu:** `Instance.pinned_to_sidebar` (registry snapshot, `#[serde(default)]`) is set by the `set_sub_pinned` RPC and only makes `sidebar-entries.ts` list the sub; the sub stays a sub (the daemon's `move_sub_to_sidebar` RPC is left but nothing in the UI calls it). A sub's images and brief come from `list_session_images` (history_scan's `facts_for`, ids read through `dashboard_gallery_image`) and `get_sub_brief` in `daemon/methods/sub_view.rs`. **Every model battery takes the effort colour:** `modelBatteryHtml(model, effort)` sets `data-effort` and `effort-battery.css` colours it (high is the default grey); a new battery goes through that function.

The Plan card keeps the finished steps and no longer draws the Result itself (only an earlier plan in the pager does). `deriveDone` (zone `done`, right column under Plan; it replaced the Finished subchats tray 2026-11-17, Joe: "15 rows is too much, I cannot tell what was done", "one row per task, not per sub") groups every sub of `DashboardInput.subs` with `kind === "finished"` into a `DoneTask`. **The grouping key is the todo id** (`todoIdOf`: the first `pc-0031`-shaped id in the sub's name, else in the first 40 characters of its latest finish verdict; nothing on `Instance` stores one, and a report text is never read since it names other todos in passing), so several chats of one todo are one row; a sub with no id groups by its name read as a title (`taskTitle`: id and dashes dropped, lowercased for the key), and a different name stands alone. The row title is the name of the first sub of the task to start (`startedAt`), the todo's own title is not looked up (a done todo leaves the backlog list). A task row says the title, a warning when any chat ended at `CTX_TOO_MUCH_PCT` (80, the status bar chip's danger tier) or more (`ctxStatusCache`, read once per finish by `ChatDashboard.ensureFinishedCtx`, so no warning until read), "N chats" and the latest finish time (`whenLabel`). A click (`DashUi.doneOpen`, task key) opens the todo id with an Open todo button (`requestTodoOpen` from `backlog-panel/backlog-open-event.ts`, only for a task with an id) and one row per chat: avatar (hover card wired once per slot in `renderZones`), verdict, finish time, context chip; a chat's click opens its finish card (`DashUi.doneCard`). The list `.dn-list` has `max-height: 260px` and scrolls (`renderZones` keeps its `scrollTop` across a redraw); the header's Clear all (`done-clear`) is always drawn. **Dismiss is optimistic** (`ChatDashboard.dismissDone`): the task's subs go into `DashUi.doneLeaving` and one `render()` draws the row with `is-leaving` (a 0.2s CSS exit), after `DONE_LEAVE_MS` they move to `doneHidden`, which `withoutHidden` filters out of the derive's `subs`; each `closeChat` runs in the background and a close that fails or is held removes the sub from both sets, so the row comes back. ## Chat heads (the chat list, pc-1769)

Read before editing `src/views/sessions/chat-heads*.ts`, `sidebar.ts`, `sidebar-ring.ts`, `src/shared/monogram.ts` or `daemon/subchats/idle_freeze.rs`. The left chat list (`.sessions-sidebar`, 260px) is gone. Chats are round **heads** stacked in the top-left corner of the chat view, under the app header. Joe's design is `docs/chat-heads-design.md`; this page is what a developer must know before editing the code. Todo: pc-1769.

`sidebar.ts`'s `renderSidebar(listEl)` stays the entry point. It calls `buildHeadEntries` and reconciles into `#sessions-list` with `reconcileList(..., animEnabled=false)`.

### The DOM contract (about 160 view specs depend on it)

- The list is `<ul id="sessions-list" class="chat-heads-list">` inside `<nav id="chat-heads" class="chat-heads">`. It has **no** `sessions-list` class, so no old row CSS can match.
- A chat is `li.chat-head[data-session-id]`; a draft is `li[data-placeholder-id]`. Both carry `data-row-key`, `data-st`, `data-kbd-hint` (1-9, normal stack only), `data-head-kind`, `data-facts`, `aria-label`. The open chat has `li.active`.
- Control heads have a `data-row-key` of `__toggle`, `__back`, `__hidden`, `__new` and a `data-heads-*` attribute. The + head keeps the old FAB's id `sessionsFab`.
- `reconcileList` skips a row whose html did not change, so anything a runtime class needs (the keyboard highlight) is part of the rendered html, read from `headsUi`, never added to the DOM afterwards.

### Rules

- **Order**: age, newest at the far end, then Joe's manual order for what he placed. Nothing re-sorts on its own. The manual order is `chatHeadsOrder` in settings.json's extra map, written with `updateSettings` (`shared/settings-update`) on the desktop, so every window agrees. The phone is refused `save_settings`, so `storeOrder` (`chat-heads-drag.ts`) sends it the finished order through the `set_chat_heads_order` RPC (`daemon/methods/chat_heads_order.rs`, transport row `P`): one key, a list of at most 300 non-empty ids, validated and deduplicated; the daemon caches it and the app process persists it and emits `settings-changed` so the desktop windows redraw.
- **Open/closed** is `headsUi.open`, in memory per window, starting open. A phone tap on a head closes it; the toggle head reopens it. Android back from a chat with the stack closed opens the stack (`chat-heads-back` event, handled in `sessions-dom-wiring.ts`).
- **Marks**: ring = state (`sidebar-ring.ts`, now with `idle` and `remote` tones), bottom-right model battery (`modelBatteryHtml`), bottom-left project badge (plain chats only), top-right red count. Everything else is in the hover card (`sidebar-hover-card.ts`, `factsFor`).
- **Hidden** chats leave the stack; the eye-slash head (with a count) shows them in place of the stack, the back head returns. The closed toggle's red count includes hidden chats that ask.
- **Ctrl+1..9** number `state.sortedSessionIds`, which `buildHeadEntries` sets to the normal stack's order. The palette (Ctrl+Shift+P) still finds every chat.
- **The open chat** is `li.active` and steps about 10px right with a white ring (`--head-ring-open`, a `--color-text` tint). The step, ring and shadow live on the `li` as `translate` and `box-shadow` transitions (200ms): the reconciler rewrites a head's insides on every update, so anything on the face could only appear, never animate. Hover nudges a head's FACE 4px right (not the `li`, or a pointer on its left edge would lose the hover and flicker), never scales it. The Ctrl highlight (`is-highlight`) steps the same way in `--color-primary`. Nothing reflows: only `translate`/`box-shadow` change, specs assert `offsetLeft/Top` are unchanged.
- **Ctrl numbers** are keycaps, the `::after` of every `li[data-kbd-hint]` (hidden at rest, so showing it is a transition and a reshuffle never replays it; `--i` from `buildHeadEntries` staggers 25ms per head on the way in). `::before` stays the drop-line. A Ctrl TAP (release before the 0.4s hold, no other key, click or blur) toggles `headsUi.open` (`chat-heads-keys.ts`); a hold keeps numbers, Up/Down and release-opens.
- **A project's main chat** is drawn as the project (`isProjectMainChat` in `chat-heads-model.ts`, shared by the head and the chat header): its head is the project face with no character, and `SessionHeader.bindSession` shows only that face and the project name (`.is-project-main`, the title node stays hidden for the title updates). Every other chat and every sub keeps the character header.
- No daemon connection and nothing to show: no heads at all (the pane shows the "Setting up" state).

### Freezing

Manual "Freeze chat" is gone (chat menu, palette, its coupling to Hidden). The sub "Pause" control stays, and so does the rate-limit auto-freeze.

The idle freeze (`idle_freeze.rs`) kills a chat's child and sets `frozen` + `auto_frozen`; `frozen_needs_continue` stays false, so waking never sends "continue". A chat qualifies only when `blocker()` finds nothing: interactive, not Jarvis or a worker, not a sub, not mirrored, not busy or compacting, `awaiting` none, `done` or `question` (a durable question card only; an open permission or secret card holds a live call and blocks, `holds_live_call`), no background task, no live sub, no held message, not closing, not under a live rate-limit window (a stamp whose reset time has passed no longer blocks: nothing clears the stamp on a timer). It must stay clear for 15 minutes (`IDLE_FREEZE_AFTER`, overridable with the `CC_IDLE_FREEZE_SECS` env var read once, on first use) by an in-memory first-seen clock and have an old `last_event_at`. A main chat past `IDLE_FLOOR_TOKENS` that idle compaction (`compaction::idle_compaction_pending`) has not yet run on is also blocked, since the compaction needs the live child at 30 quiet minutes; it is frozen 15 quiet minutes after the compaction.

`busy_watchdog.rs` is the 60 s tick; the sweep is called from `compaction::idle_sweep` so it adds no timer. The scheduler wakes an auto-frozen chat (`schedule_fire.rs` clears the pair before it fires). The front end wakes a chat when its head is opened (`selectSession` calls `unfreeze_session` silently) and on send (`sendBundle`).

**Which kind of freeze it is.** A usage-limit freeze and an idle freeze both read `frozen && auto_frozen`, and the limit stamp is wiped when any chat on the account completes a turn, so the front end cannot tell them apart from the flags. The daemon says so with `Instance.idle_frozen` (`Option<bool>`, `Some(true)` only while the sweep's freeze holds). `idle_freeze.rs` owns every write: `freeze` sets it with the stored mark (`idle-frozen<suffix>.json`), `wake` and `forget` clear both, `sync_markers` repairs drift on each sweep tick, and `persistence::populate_registry` restores it from the marks on boot. Every path that clears a freeze calls `forget` (`unfreeze_session`, `schedule_fire`), and the usage-limit freeze writer (`rate_limit.rs`) calls it too so an old mark cannot make a later limit freeze read as idle. `isIdleFrozen` and `needsFrozenLimitStrip` read the marker; an auto-freeze without it is a limit freeze (the strip shows, opening it shows the choice card). **A frozen chat that waits on a question card keeps its question state everywhere:** the head ring and count, and the dashboard's Waiting card all read `awaiting`/the transcript, never `frozen`. `sessionSegment` (no UI draws segments today; only tests call it) skips its `auto_frozen` branch for `isIdleFrozen`, so any future grouped list keeps the chat in Input Needed; a limit freeze still lands in Scheduled. Keep it that way: a new surface must not read `frozen` to mean "nothing to show". `e2e/view-harness/chat-heads-idle-frozen.view.spec.ts` pins the head and Waiting card at desktop and phone width (and the helper's segments), and that a card answered right after opening an idle-frozen chat is delivered once, after every `unfreeze_session` in flight (the open's own and `sendBundle`'s) has ended.

**Not built (needs `daemon/lifecycle/spawn.rs`, the broker's area):** a spawn-without-message wake (opening an idle chat only clears the flags; the first send still pays the respawn) and a send landing in the up-to-5 s `kill_and_wait_for_teardown` window of the freeze (it writes to a child already marked `expected_exit`; the next send respawns it).
