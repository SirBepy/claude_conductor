# Subchats (main chat, subs, cards, decisions log)

Read before editing anything under `src-tauri/src/daemon/subchats/`, the sub rules in `lifecycle` or the hooks server, `src/views/sessions/main-chat.ts`, `sub-list.ts`, `subchat-view.ts`, `src/shared/chat/subchat-cards.ts` or `permission-modal/askers.ts`.

- **Subchats module map.** A chat with "Use subchats" on (`ChatConfig.subchats_on`) hands jobs Joe names to hidden child chats (subs), whose questions and results show in the main chat's window. Everything daemon-side lives in `src-tauri/src/daemon/subchats/`; add to it rather than spreading logic through lifecycle and hook files. `brief.rs`/`spawn.rs` decide a mode-on `spawn_chat` (required brief, the three tiers, depth 1, cap of 10 started subs (`spawn/cap.rs::started_subs`: a queued sub and a never-started row with no hold hold no slot, since the cap bounds claude processes; the cap is soft: a queued sub that starts later does not re-check it, so a main chat can pass 10 while queued subs start), a duplicate name refused); `held.rs` keeps subs the daemon holds without a child (`after`, the writer queue); `worktree.rs` gives every writing sub (not a gate, not read-only) its own tree and branch at `.claude/worktrees/sub-<id>/tree` (Joe 2026-11-12: no project toggle; `ProjectConfig.subchat_writers` is still parsed and ignored), merged back with a rebase and `merge --ff-only --no-overwrite-ignore`, removed with its branch and its `sub-<id>/` holder (a `.cargo/config.toml` pointing cargo at `sub-<id>/target`, because the shared `D:/cargo-target` kept a ~3GB copy of our crates per tree path that nothing freed) only when merged, clean and with no unpublished submodule commit; removal runs git with `core.longpaths=true` and finishes a delete git gave up on (git stopped at node_modules paths over 260 chars after unregistering the tree, which stranded every tree of 2026-11-10/11), finishes a tree git left half removed, and `restore` retries at boot the trees `on_ended` marked closed (a `closed` file in the holder; a row that ended by an app shutdown or a dead process is never swept). `writers.rs` is the one-writer slot left for subs on the main checkout: a gate (a project-wide gate slot, after merges in flight) and a writer in a folder that cannot have a worktree. `finish.rs`/`turn_end.rs`/`stall.rs`/`stuck.rs`/`ceiling.rs` run a sub's end (`finish_subchat`, the Stop hook's block-nudge-card sequence, the 30-minute card, and `ceiling.rs`'s two cards: past 300 model calls, and context nearly full (90% of the window used, from the transcript's last usage line; once per round, and a long run alone never draws a card, Joe 2026-11-12); a sub queued for the writer slot, `writers::waiting_behind`, is never blocked, nudged or carded as stalled, a turn opened by a new message starts a new block-nudge round, and Joe's failed "Nudge again" draws one "did not help" card, never the same card again); `queue_watch.rs` wakes a main chat once when a sub has waited 5 minutes with nothing in its way (its `after` finished cleanly, the slot is free, or its hold is gone), and `card_watch.rs` wakes it once when a sub's stall card (stuck, stopped, died) has gone 10 minutes without Joe's answer, so a main chat never schedules prompts to poll its subs; `routing.rs` stamps `display_session_id` on question, permission and secret payloads so a sub's card shows in its main chat while `session_id` stays the answer target. `card_log.rs` stores the cards a sub draws in its main chat (`facts.rs` computes their chips from git and the transcript), `back.rs` queues the one line served on Joe's next message, `decisions.rs` keeps the decisions log (there is no "checkup" of it: that card read as noise and was removed 2026-11-12, so a finish never runs a model or raises a card), `closing.rs` holds a close that would strand running subs or unmerged worktree commits and moves a family on `respawn` or promotion, `reply.rs` is typing to a sub and "Move to sidebar", `adopt.rs` is the reverse ("Move into main chat" in the chat menu: placeholder brief, an idle child is stopped so the next send relaunches it as a sub, the main chat is woken to hand it a job), `tool.rs` is the `subchat` MCP tool, and `jsonfile.rs` keeps an unreadable state file aside as `.bad` instead of reading it as empty. **The seams:** `subchats::is_sub(&Instance)` is how any list or rule asks "is this a sub" (`subchat_of`, never `worker_of`: a sub must not wake its parent the way a Jarvis worker does); `subchats::on_finished(state, sub_id)` is the one hook a finish fires (card, one line back, decisions, `after` queue, wake); `cards::raise_card` is the only way the daemon puts its own question card in a window; `subchats::role_launch` decides on every launch whether a row is a sub, a main chat or neither. **Data files** are under `<data_dir>/subchats/`: `<main>.cards.jsonl`, `<main>.pending.jsonl`, `<main>.decisions.md`, `<sub>.finish.json`, `<sub>.digest.md`, `<sub>.ceiling.json`, `held[suffix].json` (per daemon instance: a test or dev daemon on the same data folder has its own registry, and a shared file let every `cargo test` wipe the live queue, 2026-11-10). A leftover `checkups.json` from an older build is never read. A sub that never started and lost its hold is rebuilt from its brief by `held::recover_lost` only within `RECOVER_WITHIN` (2h) of its spawn; an older one is left to the watchdog and the `subchat drop` action. **Hard rules:** a sub's text never travels inside an `is_meta` message (only as hook context framed as data, `back.rs` and the decisions rider); a sub is never `worker_of`; only the daemon writes the decisions log, so no chat carries it; every field of `held.json`'s entries except the sub id has `#[serde(default)]` and an unreadable file or entry is kept as `.bad`, never read as empty. Frontend: `src/views/sessions/main-chat.ts` (`mainChatInfo`, `showsSubs`: the sidebar row's dots, count, hover and ring), `sub-list.ts` and `subchat-view.ts` (header count, list, reading a sub in place), `src/shared/chat/subchat-cards.ts` and `chat-subchat-card.ts` (cards and chips), `permission-modal/askers.ts` (chips for several askers in one window). What a paired machine sees: `docs/multi-machine.md`.
