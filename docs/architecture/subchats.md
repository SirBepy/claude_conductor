# Subchats (main chat, subs, cards, decisions log)

Read before editing anything under `src-tauri/src/daemon/subchats/`, the sub rules in `lifecycle` or the hooks server, `src/views/sessions/main-chat.ts`, `sub-list.ts`, `subchat-view.ts`, `src/shared/chat/subchat-cards.ts` or `permission-modal/askers.ts`.

- **Subchats module map.** A chat with "Use subchats" on (`ChatConfig.subchats_on`) hands jobs Joe names to hidden child chats (subs), whose questions and results show in the main chat's window. Everything daemon-side lives in `src-tauri/src/daemon/subchats/`; add to it rather than spreading logic through lifecycle and hook files. `brief.rs`/`spawn.rs` decide a mode-on `spawn_chat` (required brief, the three tiers, depth 1, cap of 10 started subs (`spawn/cap.rs::started_subs`: a queued sub and a never-started row with no hold hold no slot, since the cap bounds claude processes; the cap is soft: a queued sub that starts later does not re-check it, so a main chat can pass 10 while queued subs start), a duplicate name refused); `held.rs` keeps subs the daemon holds without a child (`after`, the writer queue) and `lost_hold.rs` rebuilds the hold of a sub that never started and lost its entry; `worktree.rs` gives every writing sub (not a gate, not read-only) its own tree and branch at `.claude/worktrees/sub-<id>/tree` (Joe 2026-11-12: no project toggle; `ProjectConfig.subchat_writers` is still parsed and ignored), merged back with a rebase and `merge --ff-only --no-overwrite-ignore`, removed with its branch and its `sub-<id>/` holder (a `.cargo/config.toml` pointing cargo at `sub-<id>/target`, because the shared `D:/cargo-target` kept a ~3GB copy of our crates per tree path that nothing freed) only when merged, clean and with no unpublished submodule commit; removal runs git with `core.longpaths=true` and finishes a delete git gave up on (git stopped at node_modules paths over 260 chars after unregistering the tree, which stranded every tree of 2026-11-10/11), finishes a tree git left half removed, and `restore` retries at boot the trees `on_ended` marked closed (a `closed` file in the holder; a row that ended by an app shutdown or a dead process is never swept). `worktree_safety.rs` adds two refusals to removal: a tree holding files git ignores that the setup did not make (`status --ignored`, build output such as `target` and `node_modules` excluded, the setup's own output recorded in `<git dir>/cc-setup-ignored`) and a detached HEAD whose commits no branch or remote holds; a merge in flight is held by a `MergeGuard` that releases on drop, so a panic or a never-started merge thread cannot leave `merging()` true; `update_branch` writes a `cc-rebasing` marker before its rebase, and a rebase in progress WITH the marker (the daemon died inside it) is aborted so the land can retry, one without it (the sub's own conflict) is never touched. `build_target.rs` frees a sub's private cargo `target` (`sub-<id>/target`, kept apart from the tree so the tree can stay) when the sub finished and landed, and `restore` sweeps the targets of finished, idle subs older than 3 hours by directory mtime, logging one INFO size line; it never deletes outside `<repo>/.claude/worktrees` and never touches a row that is busy, held, queued or has a pending merge. `writers.rs` is the one-writer slot left for subs on the main checkout: a gate (a project-wide gate slot, after merges in flight) and a writer in a folder that cannot have a worktree. `finish.rs`/`turn_end.rs`/`stall.rs`/`stuck.rs`/`ceiling.rs` run a sub's end (`finish_subchat`, the Stop hook's block-nudge-card sequence, the 30-minute card, and `ceiling.rs`'s context bands (no card: Joe 2026-11-16, "stop asking me how many calls or how many tokens, if we agreed it resets at a point, reset it"; a long run alone, a call count or a size never asks Joe anything); a sub queued for the writer slot, `writers::waiting_behind`, is never blocked, nudged or carded as stalled, a turn opened by a new message starts a new block-nudge round, and Joe's failed "Nudge again" draws one "did not help" card, never the same card again); `queue_watch.rs` wakes a main chat once when a sub has waited 5 minutes with nothing in its way (its `after` finished cleanly, the slot is free, or its hold is gone), and `card_watch.rs` wakes it once when a sub's stall card (stuck, stopped, died) has gone 10 minutes without Joe's answer, so a main chat never schedules prompts to poll its subs (every daemon-built wake of a main chat about a sub goes through `wake::wake_main_chat`, the one enqueue-and-drain, and `wake::short_and_shown` words the name; `card_watch` wakes once per sub per stall episode, not once per card: an episode ends when someone sends the sub a message (`resume::prepare_continue` and the live-child branch of `reply::route_send` call `card_watch::new_round`) or it finishes or ends, never on the daemon's own nudge, so a sub that waits on purpose draws one wake, not one per turn it ends unfinished); `plumbing.rs` is the rule that a sub's plumbing never reaches Joe as a card (Joe 2026-11-12: a sub that could not start, a worktree or bootstrap failure, a refused merge, a conflict the sub did not fix after `merge_followup` told it once, a continued branch that could not be updated): it wakes the main chat once per problem with fixed words, `subchat status` returns what failed as tool data, and the main chat fixes it with `subchat retry` (`held::retry`, start a sub whose start failed), `merge` (`merge_followup::merge_now`, land a finished sub's refused merge) or `drop` (a never-started sub, or giving up a refused merge so its commits stay on the branch), asking Joe only when it needs his decision; a merge refused because another chat has uncommitted changes in the same files raises nothing and wakes nobody: `pending_merges.rs` keeps it on disk and the busy_watchdog tick lands it (`merge_followup::retry_pending`) once those files are clean; every other refused merge is kept in the same file until it lands or is dropped, so `merge_followup::unresolved` keeps an `after` sub waiting across a restart too; a removed-worktree card on an ended sub (`worktree::on_ended`, tree kept or build folder left) is the one plumbing card left, as the record of where unmerged commits sit; `routing.rs` stamps `display_session_id` on question, permission and secret payloads so a sub's card shows in its main chat while `session_id` stays the answer target. `card_log.rs` (the log file, entry types and storage; `card_log/` holds `blockers`, `answers`, `reports` for the finish and all-finished cards, and `remote_cards`) stores the cards a sub draws in its main chat (`facts/` computes their chips from git and the transcript), `back.rs` queues the one line served on Joe's next message, `finish_subchat` requires `decided`, `ruled_out` and `learned` (each a list of at most 8 rows of 200 chars, `["nothing"]` is valid, a refusal names every field left out): `learned` lists what the job taught that stays true, each row naming the memory file or todo id the sub saved it to first with the save step (`~/.claude/refs/save-step.md`), is stored on `FinishRecord` and is deliberately not copied to the decisions log or the digest, `decisions.rs` keeps the decisions log (there is no "checkup" of it: that card read as noise and was removed 2026-11-12, so a finish never runs a model or raises a card), `closing.rs` holds a close that would strand running subs or unmerged worktree commits and moves a family on `respawn` or promotion, `reply.rs` is typing to a sub and "Move to sidebar", `adopt.rs` is the reverse ("Move into main chat" in the chat menu goes straight into the chat's own project's live main chat with a toast, the previous main chat first else the newest, and opens a picker only when the project has none; placeholder brief, an idle child is stopped so the next send relaunches it as a sub, the main chat is woken to hand it a job), `tool.rs` is the `subchat` MCP tool, and `jsonfile.rs` keeps an unreadable state file aside as `.bad` instead of reading it as empty. **The seams:** `subchats::is_sub(&Instance)` is how any list or rule asks "is this a sub" (`subchat_of`, never `worker_of`: a sub must not wake its parent the way a Jarvis worker does); `subchats::on_finished(state, sub_id)` is the one hook a finish fires (card, one line back, decisions, `after` queue, wake); `cards::raise_card` is the only way the daemon puts its own question card in a window; `subchats::role_launch` decides on every launch whether a row is a sub, a main chat or neither. **Data files** are under `<data_dir>/subchats/`: `<main>.cards.jsonl`, `<main>.pending.jsonl`, `<main>.decisions.md`, `<sub>.finish.json`, `<sub>.digest.md`, `held[suffix].json` and `pending-merges[suffix].json` (per daemon instance: a test or dev daemon on the same data folder has its own registry, and a shared file let every `cargo test` wipe the live queue, 2026-11-10). A leftover `checkups.json` from an older build is never read. A sub that never started and lost its hold is rebuilt from its brief by `lost_hold::recover_lost` only within `RECOVER_WITHIN` (2h) of its spawn; an older one is left to the watchdog and the `subchat drop` action. **Hard rules:** a sub's text never travels inside an `is_meta` message (only as hook context framed as data, `back.rs` and the decisions rider); a sub is never `worker_of`; only the daemon writes the decisions log, so no chat carries it; every field of `held.json`'s and `pending-merges.json`'s entries except the sub id has `#[serde(default)]` and an unreadable file or entry is kept as `.bad`, never read as empty. **A project knows its main chat** (2026-11-12, D1): `ProjectConfig.main_chat_id` (`#[serde(default)]`) names the one live main chat per project. `main_pointer.rs` keeps it true to the registry: `reconcile` keeps a live pointer, replaces a dead one with the project's newest live mode-on chat and clears it when none is left, and runs from `publish_mode_changed` (every mode flip, so a menu flip and the `start_session` rollback), after `start_session` registers a new main chat (its mode is written before the row exists), from `settle_family` (every close path settles after it marks the row ended), and from `heal_orphans` at boot and on the 60 second tick; a `respawn` successor takes the pointer through `hand_over`. The daemon never writes settings.json: it sets its cache and publishes `project_main_chat_set`, which `daemon_link/handlers.rs` merges and persists. The pointer is read by the draft and the sidebar from `list_projects` (`project-main-chats.ts`, re-read on `settings-changed`, the `subchats-on-changed` nudge and at mount), and a reader always checks the chat it names is still open, since the heal can lag a crash by a minute. Closing the pointed chat is a put-away since pc-1806 step 3 (see the bullet below: nothing is deleted or ended and the pointer stays); an ordinary chat with a running sub or unmerged commits still asks first (`closing::needs_approval`), and `APPROVED` keeps the pump's EOF backstop from raising a second card for a close Joe already approved. A new chat in a project with a main chat (`draft-subchats.ts`) shows "Goes to <title>, <project>'s main chat" and a Plain chat instead switch where Use subchats sits, and sends its first message to that chat (`pending-pane-composer.ts::sendToMainChat`, a scheduled message goes there too); with Plain chat instead on the draft is an ordinary chat with the mode off. The sidebar's Main chats group lists only the pointed chat of a project (`listedAsProjectMain`); a second mode-on chat in the project draws in the group its state puts it in. With no pointer loaded (a phone whose project list failed) every mode-on chat lists as before. Frontend: `src/views/sessions/main-chat.ts` (`mainChatInfo`, `showsSubs`: the sidebar row's dots, count, hover and ring), `sub-list.ts` and `subchat-view.ts` (header count, list, reading a sub in place), `src/shared/chat/subchat-cards.ts` and `chat-subchat-card.ts` (cards and chips), `permission-modal/askers.ts` (chips for several askers in one window). What a paired machine sees: `docs/multi-machine.md`.

- **Big subchats files are split by responsibility, and every public path stays** (2026-11-20, pc-1797 and pc-1767's structure items; no behaviour change). The parent file keeps the header, constants and a `mod x; pub use x::*;` list, and each child starts with `use super::*;`, so `worktree::land`, `tool::send` and the like still resolve. A top-level item that was private in the parent is `pub(super)` in its child, and one that was `pub(super)` (visible to `subchats`) is `pub(in super::super)`, so a call from another subchats file keeps working. Layout: `facts/` (`mod.rs` the types, git side and `compute`; `scan.rs` the transcript scan, test judging and `ReviewGap`; `sum.rs`), `decisions/` (`format`, `store`, `write`, `digest`), `worktree/` (`create`, `setup`, `update`, `land`, `sweep`, beside `removal`), `tool/` (`view`, `send`, `remote`), `compaction/` (`state`, `decide`, `context`, beside `save_step`), `hooks_server/publish_matcher/` (`heredoc`, `words`, `programs`). Each keeps its tests in the folder's `tests.rs`. Add new code to the child that owns the responsibility, not back to the parent.
- **Main chat digest.** A main chat never closes, so no model turn writes its recall digest: `decisions.rs` rewrites `<data dir>/subchats/<main chat session id>.digest.md` from the chat's decisions log every time the log changes (`append_in`, the one write path every card answer and sub finish goes through, plus `move_log` on a respawn), in the same folder and four-section format as a sub's digest. Live `card` and `decided` entries become `## Decided`, `ruled_out` entries `## Rejected`, replaced entries are left out, `## Done` names the subs that reported rows, and `## Open` is `none`; a log with nothing decided or ruled out writes no file. The global `recall` tool ingests it with the sub digests, and only the daemon writes it.
- **Moving a main chat and its subs to another account** (Joe 2026-11-13, D67-D69). The Change account picker (`change-account-modal.ts::openChangeAccountForChat`, opened from the chat menu, the statusbar account chip and the rate-limit banner's Switch account) shows "Also move its N subchats", on by default, on a chat with subs that have not ended. `account-move.ts` then calls `move_session_to_account` once per chat, main first, skipping any already on the target, so a working sub restarts on the new account at once and gets "continue", the same as a single move. Subs started later copy the main chat's account, so they follow with no extra state. API credit is left out of that picker for a sub, a mode-on chat or a chat with subs, and `subchats::refusal_for_move` refuses it in the daemon too, the third door after the mode toggle and the sub spawn. The rate-limit banner never picks a target itself: an account it guessed could be the one that is not working.

- **`after` takes a list, and a sub's context reaches its main chat** (2026-11-14). `spawn_chat`'s `after` is a name or an array of names; both reach the daemon as one string, a name per line (`brief::after_names`), and `Held.after`/`after_name` hold one id and one name per line the same way, so an entry written before lists existed still reads as one target. `held::after_all` is the one verdict over them: blocked as soon as any one ended blocked (the card names that sub), clean only when all finished cleanly. `ceiling::context_pct` is the sub's context share in whole percent, shown as `context_pct` by `subchat list` and `status`; the 60 second sweep also wakes the main chat once per band at 60 and 75 (`CONTEXT_BANDS`, text from ids and a number only), and there is no 90% card any more. **Sub size (pc-1752 and pc-1754, 2026-11-16):** (1) a sub compacts itself: `lifecycle/spawn.rs` sets `CLAUDE_CODE_AUTO_COMPACT_WINDOW=300000` on a sub's child (spiked on claude 2.1.325: the CLI compacted twice inside one turn, which the daemon's turn-end compaction cannot do for a sub whose growth is one long turn); `compaction::session_start_answer` then hands a compacted sub its brief word for word, `git status`, `diff --stat` and its own decisions rows (`sub_session_start_context`, hook context, never message text); a compaction mid-turn raises no stall and no nudge since no turn ends. (2) `subchat send` refuses a writing send, or any send after the finish, to a sub at or past the first band (`ceiling::heavy_send_refusal`, `ok:false` naming `continue_from`); a question inside a running round still goes through. (3) `spawn_chat` `continue_from: <sub name>` (idle or finished writing sub of the same main chat, here, no `after`): `worktree::plan_continue` commits the old tree's uncommitted work as a WIP commit and `prepare_at` starts the new tree from that commit; once the new sub is registered `worktree::hand_over` detaches the old row's tree, ends it and removes its tree and branch against the successor's branch (every commit is on it, the usual clean and no-ignored-work checks still apply); the new first message names the old sub by id and sanitised name only. (4) The decisions log shows a sub Joe's card answers, rows starting `rule:` (a convention for the whole project, at most 3) and its own rows; another sub's `decided` and `ruled_out` rows stay in the file but are not injected (`decisions::visible_to`), and a sub's `replaces` row never closes a card answer. (5) The stuck sweep raises one card per turn (`runtime::stuck_carded_gen`), so a sub that waits on purpose does not wake the main chat every half hour; UNVERIFIED which stall kind produced the 2026-11-14 repeats, the app log from that day is gone (the log keeps one file, `Claude Conductor.log`). A sub closed from the UI goes through `end_sub` (`mark_session_ended`), the same end as the daemon's "End it". A target that read as finished cleanly goes on `Held.cleared` (`#[serde(default)]`) and later checks skip it once it has ended (one that went back to work is read again), so closing a merged sub while a sibling target still runs raises no "ended before it finished" card; a target closed before it read clean (a refused merge dropped by the close) still counts as blocked. A scheduled new chat the start cap refuses (`SPAWN_CAPPED:<secs>`) is requeued like a rate-limited one.

- **A sub's answers and drafts reach its main chat** (2026-11-15). `hooks_server/messages/mod.rs::draw_sub_card` draws a sub's `send_message` of kind `blocker`, `answer` or `rating` into the main chat through `card_log.rs` (`on_blocker`, `on_answer`); every other kind (report, plan, progress) stays in the sub. An answer card keeps the whole message: `text`, `points`, `details` (`CardEntry.details`, so the `[label](#d:id)` links open), `visuals`, and its `question`, which is the one the send carried or else the brief's pending one, spent from the brief at once so the sub's later finish is not a second answer to it. `update_message` from the sub rewrites or retracts the card it drew in the same turn (`send_answer_update`, remembered per sub and turn gen in `TURN_SENDS`; the daemon never learns the ordinal `update_message` counts by, so an update of an older turn's message is not mirrored) and announces it again as a `subchat_card` frame with `replace: true`, which `ChatRenderer.onSubCardFrame` swaps in place. The Messages view tags the card with the sub's name (`renderSubCard`); the Answers card counts it through `answers-model.ts::isSubAnswer` (`kind` answer or rating, question optional, filling that sub's pending hand-off row at once). A sub's `write_draft` stamps `MessageDraft.origin_main_session_id` (its `subchat_of`, `#[serde(default)]`; `closing::move_family` rewrites it on a `respawn` with `message_drafts::rehome_main`), and the dashboard's Drafts card (`drafts-model.ts`) lists a draft when that field names this chat or, for one written before the field existed, when its `origin_session_id` is a live sub or a sub of the card log (a closed sub's drafts still list), each labelled `from <sub name>`. The sub prompt (`claude_config/args.rs` `SUBCHAT_SUB_PROMPT`) tells the sub which kinds reach the window.

- **Cross-machine subs** (a main chat here, its sub on a paired machine): design, trust rules, wire and build steps in `docs/cross-machine-subchats.md`. Read it before touching `subchats/remote/` or any sub path that runs on a sub's host instead of its main chat's daemon. A visiting sub's `send_message` cards (`blocker`, `answer`, `rating`) never draw on the host: `card_log::on_blocker`/`on_answer` queue an `Event::Card` and the home draws it (`draw_remote_card_at`); Joe's answer to its question is logged on the home only (`decisions::record_remote_card_answer`, called by `machines/forward.rs`), and `card_ctx` writes nothing for a visiting sub. `scripts/cross-machine-verify.mjs` is the two-daemon live run. **Offload (pc-1782):** `spawn_chat_or_forward` calls `subchats::remote::offload::try_offload` BEFORE the local path's `spawn_rate::admit("spawn_chat")`, because a scratch spawn counts itself once after the host took it, so a local admit ahead of the call would count it twice (`loopback_tests::spawn_chat_with_the_switch_on_places_a_reader_on_the_machine_and_counts_it_once` drives the real entry and asserts one count; `offload::set_test_bar` lowers the free-disk bar for one test thread). The seam is wired, the switch (`offloadReadOnlySubs`) stays off by default until a real Mac has passed the acceptance, and the run's `offloadScenario` covers a reader placed on the host in a scratch folder and the same spawn running on the home once the host is gone.

- **The chat start cap counts starts, not registrations** (2026-11-21). A sub registered queued (`after`, the writer slot, a worktree) is only `spawn_rate::check`ed in `spawn_chat`; `held::launch_claimed` calls `spawn_rate::record` when its child actually starts (a held remote sub counts on the home in `remote/actions.rs::start`; the host's `sub_spawn` only checks, because every host sub starts through `launch_claimed`), and only a child that starts at once goes through `admit`/`gate(.., true, ..)`. `record` never refuses, so a chain registered while the budget is empty may start more than `LIMIT` in one window; the next registration is refused until it clears. A main chat's chain of 20+ queued subs is accepted, and a refusal of a sub spawn returns as the tool error alone: `spawn_rate::card_wanted` gates `tell_joe`, so the Tooling card is only for a loop with no main chat's sub behind it (plain chat, schedule, Jarvis), and a sub refusal does not use up the burst's one card (`Starts::check`'s `quiet`).

- **Is the main chat still there** (2026-11-15). Every sweep that drops or settles subs because their main chat is gone (`held::orphaned`, `closing::heal_orphans`, `queue_watch`) asks `held::chat_live`: the chat's row is open, or the daemon holds its child. A row alone is not enough, because a row can stay `ended_at` while the chat runs again (a SessionEnd hook closed an External row, then a scheduled wake resumed it, and the sub it spawned next was dropped with its half-set-up worktree). `schedule_fire::reopen_ended_row` reopens such a row after a wake, and a launch whose sub ended during its worktree setup stops with `held::ENDED_BEFORE_START` and tells nobody. `held::release` logs its caller, so a hold that vanishes is traceable. `subchat status` and `list` read a sub that ended its turn to wait on its own background job (`Instance.local_task_running`) as working, progress "waiting on its background task".

- **A sub's tree is removed when it is merged and clean, and the submodule commits only it holds are saved first** (2026-11-16, `worktree/removal.rs` and `worktree/removal/module_keep.rs`). A worktree's submodules keep their git dirs inside the worktree's own, and `git worktree remove` refuses any tree with an initialised one, so the removal ends in `--force`, which deletes them. Before that, `keep_modules` fetches the tip of every module's HEAD, local branches, tags and every stash entry that holds a commit no `refs/remotes` ref has, and every commit the tree's own parent recorded for the module (its index entry and the last 200 commits that touched it) that no remote has, into the MAIN CHECKOUT's copy of the module (`repo/<path>`) as `refs/cc-sub-kept/<sub id>/<n>`, reads each ref back, and only then lets the removal go on: a merged, clean tree is never kept just because its module has unpublished commits, and Joe gets no card for it. A module pointer the tree moved to a commit the branch never recorded shows as ` M <path>` in the parent's status; `drifted_modules` keeps that out of "uncommitted work", and the commit it points at is saved even when a remote has it, because the parent's record of it goes with the tree. A module NESTED in another is recorded by the module around it, so `drifted_modules` reads the status of each module that owns one (not only the tree's) and returns paths from the tree's root; the owner then lists the nested module as ` M` (moved) or the module around it as ` m` (something inside it differs), and `keep_modules` drops a nested drift from that module's own dirty list (the nested commit is saved by its own tips) while real work in the nested module still keeps the tree (2026-11-18, pc-1764). Still kept, with a card: a tree whose submodules `git submodule status --recursive` cannot list, a module whose stash (`refs/stash` exists but `rev-list -g` fails, so the older entries on a corrupt reflog would read as no stash) or whose recorded pointers (`ls-files`, `log` or `ls-tree` fail) cannot be read, which is an error and never "nothing" (2026-11-18, pc-1764), a module with uncommitted work (checked in every module before anything is saved, so a kept tree is left as it was apart from a scratch ref `refs/cc-sub-keep-src/<n>` inside the module's own git dir), one that cannot be checked, one the main checkout never set up (no `.git` in `repo/<path>`, so there is nowhere to save), and a failed or unverified save. Recover a kept commit with `git -C <main checkout>/<path> branch <name> refs/cc-sub-kept/<sub id>/<n>`; nothing prunes these refs. The rule line in CLAUDE.md ("removed only when merged, clean and with no unpublished submodule commit") should now read "removed only when merged and clean; a submodule commit no remote has is saved first under `refs/cc-sub-kept/` in the main checkout's module, and the tree stays only when that save is impossible".

- **Every start and wake obeys the hidden family (pc-1806 step 2, 2026-11-21).** The gate is `put_away::is_gated(state, id)`, true for a put-away main chat and for any sub of it (`family_main` resolves a sub through `Instance.subchat_of`; the record is keyed by the MAIN id). A start refuses with `LifecycleError::PutAway` whose text starts `put_away::REFUSAL_PREFIX` (`PUT_AWAY:`, load-bearing like `SESSION_BUSY:`; the RPC maps it to invalid params) and changes nothing, so a refused call never thaws a freeze or clears a finished mark. The doors, each with a test: `refuse_if_put_away` in `lifecycle/spawn.rs` (called first by `spawn_session_inner`, by `refuse_if_frozen` so an idle freeze is never woken, and by all three `send_message_with_respawn*` doors; a brand-new sub is caught through `sub_parent`), `restart_session` and `respawn_interactive` (before the kill, so a refused restart tears nothing down), the `send_message` RPC, the phone's REST send (`remote_handlers::deliver_send`, first of its side effects, answers 423 so the held queue does not re-stage it), the mockup message door (`methods/preview.rs` `deliver_user_text`), `remote::actions::start` (the door of every held remote start: sweep, card answer, Start now; `remote::actions::retry` guards its own; a refusal is never parked or reported), `queue_watch` and `remote::after::stalled_tick` (a withheld start is no stall), `unfreeze_session`, the account move, `idle_freeze::wake`, `resume::prepare_continue`, the schedule (`compute_fired` DEFERS a message to a gated chat as Pending at its own `fire_at`, never Failed or sent; `fire_message` refuses as a belt, before it clears an auto-freeze), `resume_interrupted::spawn_resumes` (filtered before `queue`, so the dead sweep never reads a skipped chat as about to resume), the `peer_scope` check (any peer, driving or view-only, on any acting method; reads and chat starts pass), `held::register_row` and `spawn::plan_at` (a put-away main chat plans and registers no sub), `held::launch_claimed` and `writers::run_start` (a gated Launch keeps its hold and leaves the writer queue; a gated Wake does nothing; a refused held start is never parked nor reported, `held::is_put_away_refusal`, so a card answer or a retry cannot strand the sub past a reopen), and both after-release passes (`held::release_ready` and `remote::after::release_ready` still record `cleared` but start nothing, and a blocked target raises no card). Wakes of the main chat do not queue per-sub text: `wake::wake_main_chat` folds every sub change into ONE daemon notice "N subs changed while this chat was put away" (`repo_channel_wake::enqueue_folded_notice`, bumped in place and kept on disk like any notice), and `drain_with` leaves the queue untouched while gated. Daemon notices are never dropped to make room (`make_room`): a full queue refuses the next PEER line instead, since a put-away chat can hold them for days. `auto_close::is_due` skips a finished sub a live held sub still waits for (its `cleared` mark is the release). What a reopen (step 6) owes: drain the wake queue, call `held::requeue_held`, and nudge writer-slot holders that were taken out of line (a gated Wake has no queue entry to re-run). A text sent to an already running remote sub (`remote::actions::deliver_noting_wait`) is refused with the same `PUT_AWAY:` text before any call to the host, and `merge_followup::tell_remote` reads that refusal as nothing failed (no Conflict problem). Known gaps: a put-away sub that holds its project's single writer slot keeps it (other families' writers in that project queue behind it until the reopen or the sub's end), the stuck and stall dead sweeps still card a gated sub, a schedule item for a family that stays put away goes Missed past its grace window (a recurring one moves on), and a NewChat schedule into a project whose main chat is put away is step 6.

**Visiting subs of a put-away chat (pc-1806 step 4, 2026-11-21).** The HOME owns the family and the gate, the HOST runs the sub, so the home's put-away reaches the host through the outbox. `put_away::flow::plan` lists every live remote sub (`plan_remote`: `PausedSub.machine_id` names the host, prior from the record's state) and `run` calls `queue_remote_pauses` right after the quiet-wait check (an undone put-away queues nothing): per sub an ordered outbox entry `sub_pause {sub_id}` through `remote::actions::queue_pause`. The host's `sub_pause` (`host_actions::pause`, an `M` row, `own_sub` checks `ctx.transport` against the stored home) records the sub in `<data_dir>/subchats/<main>.visiting-paused.json` (`put_away/visiting.rs`: the file also closes the host's own gate, `is_hidden_in` reads it, fail-closed like the home record) and runs the local `put_away::pause_sub` detached under a `PAUSING` claim, so the sub stops at its next turn end, never mid-turn. `sub_resume {sub_id, send_continue}` (`actions::queue_resume`, queued after the pause so a late pause cannot follow it) opens the gate, waits for the `PAUSING` claim, then sends the "continue" nudge when the freeze carried `frozen_needs_continue` and the home asked for it, or only unfreezes. `sub_end`, `sub_drop` and `sub_to_sidebar` drop the sub from the visiting file but never open the gate. The home meanwhile keeps a visiting sub's `sub_event` without drawing it: `home::apply` holds the event in `<main>.remote-held.json` (`remote/held_events.rs`, 500 at most; full answers -32603 so the host's outbox retries), notes its seq (a resend is a duplicate) and answers ok, and `home::release_held_events` applies them in arrival order once the family is open (called by `held::sweep` through `release_all_held_events`, and by the reopen). While anything is kept, a live event joins the list even after the reopen (`held_events::any`), so it never overtakes the kept ones, and an event that meets the pass applying the same sub gets an internal error (the host sends it again), never `Duplicate`. The host's `sub_resume` checks the caller by the stored brief alone when the row is gone (`own_brief`), so a pruned sub cannot keep the gate shut, and a sub that ends on the host itself drops off the file through `events::on_ended`; a failed "continue" puts `frozen_needs_continue` back and answers an internal error so the outbox retries. Gaps: a crash between applying a kept event and removing it re-applies it (a Card, Wake or Notice would draw twice; Finished is guarded by its round), a host restart while a sub is paused loses `needs_continue` (the gate keeps the child down, a resume only unfreezes), a Finished or Ended state at the home lags until the reopen, and step 6 (reopen) must call `put_away::reopen`, `home::release_held_events`, `actions::queue_resume` per paused remote sub (the record's `machine_id`) and `clear`.

- **Closing a project's main chat is a put-away (pc-1806 step 3, 2026-11-21; `put_away/flow.rs`, `closing.rs`).** `closing::close_outcome` (`Proceed | Held | PutAway`; `request_close` is `!= Proceed`) asks `put_away::is_project_main_chat` first (open, local, not a sub, `Interactive`, named by a project's `main_chat_id`, no live `respawn` successor, not an approved close) and starts `flow::run` detached. Every close door gets it: `close_session` (`on_close_confirm` answers `ok:false` with `put_away::NOTE`, arms no teardown), the `end_session` and `mark_session_ended` RPCs (`{"ok":true,"held":true,"put_away":true}`) and the pump backstop. It never calls `complete`, `mark_ended`, `drop_for_chat` or `settle_family`: no sub ends or moves to the sidebar, no Answers or Ask store goes, no History entry is made (the row stays open) and the pointer stays; the family's cards are parked by not being touched. `needs_approval` no longer special-cases the pointer and `main_chat_line` is gone, so the approval card (an ordinary chat with a running or unmerged sub) never names a main-chat cost. **Order of `flow::run`:** (1) the pending "Wait for them" or card is forgotten and the plan of paused subs is read (prior `Finished`, `Held`, `Working` when `busy`, `local_task_running` or a card is open, else `Idle`; `needs_continue` is the `Working` test); (2) `put_away::put_away` writes the record FIRST and the snapshot is saved, which closes the gate of step 2 before anything else; (3) the chat's own turn and any save turn or compaction in flight are waited out (`Timing::quiet_wait`, 30 min; the `close_session` call itself arrives inside a turn), and a chat still busy after it is NOT put away: `reopen` plus `clear` undo the record and the chat stays as it was; (4) `compaction::start_for_put_away` runs the save step and a compaction while the cache is warm: `Trigger::PutAway` ignores the project's auto-compact switch but keeps the API-credit refusal (`decide::put_away_size_gate`) and the 150K floor, and the compaction is waited for (`compaction_wait`, 20 min) through `compaction::in_progress`, which also covers the 5 s settle between a save turn's end and its `/compact` (`Chat.after_save_pending`; `is_compacting` alone reads that gap as done); (5) every local sub is paused in parallel at its NEXT turn end: wait for `!busy` (`sub_wait`, 6 h; a sub still busy then keeps running and the record says paused), then `freeze_child` stops the child and marks the row frozen with `frozen_needs_continue = needs_continue` and `writers::release_for_pause` lets go of the slot it holds; (6) the main chat's child is stopped last (only when its compaction finished). The freeze is the MANUAL kind (`set_frozen(true)` after `kill_and_wait_for_teardown`), not the idle one: no schedule, rate-limit resume or send clears it, only a reopen does, and the stuck and dead sweeps skip it. A finished or held sub has no child and is left as is, a sub with a permission or secret card open (`holds_live_call`) is left running because killing it would expire the card. `writers::advance_locked` passes over a gated entry without removing it (a paused family keeps its place in line, and the next family that can start takes the slot; with only gated entries in line the slot stays free until a reopen), and `release_for_pause` only clears the holder. `flow::pause_now` is the "pause now" escalation (interrupt through `cancel_turn`, wait `interrupt_wait` for the result line, `kill_tree` only as the fallback, `needs_continue` true): nothing in the app calls it yet (step 5 adds the button). `respawn` from a project's main chat is refused (`put_away::refuse_respawn`, the top of `spawn_chat`; a respawn would end the chat for real and compaction keeps it small); `SUBCHATS_MAIN_PROMPT` rule 12 says the chat is put away, not ended. A sub that kept its child (a card open) keeps the writer slot, and the Stop hook (`hooks_server/stop.rs::sub_stop`) exempts a put-away family's subs so the turn end the pause waits for is not blocked into another turn; a writer arriving at a free slot with only gated entries in line takes it (`free_for_a_newcomer`). Known gaps: a sub on a paired machine is not paused (step 4), a flow that times out or is refused (`NotQuiet`, no runtime) only logs a warning although the caller was told "put away", `needs_continue` is read once when the put-away begins, the reopen side (drain the wake queue, `held::requeue_held`, nudge slot holders, "Continue the plan?", and the reopen itself) is step 6 and until it lands nothing reopens a put-away chat, and the context nudge and cap cards (`context_nudge.rs`, `context_cap.rs`) still tell a main chat to `respawn`, which `refuse_respawn` now refuses.

- **Put away in the UI (pc-1806 step 5, 2026-11-21; `src/views/sessions/put-away.ts`).** The front end reads the daemon's `Instance.hidden_at` through that one file (`isPutAway`, `putAwayMainOf`, `inPutAwayFamily`, `pausedSubs`, `putAwayLine`, `hiddenIdsOf`); nothing else tests it. A put-away main chat and its pinned subs join the Hidden view (`hiddenIdsOf` is the hand-hide list plus the family, so the eye's count, the stack and the toggle's red count read one set; a waiting card behind a put-away chat stays counted), and the head wears `.chat-head-paused` (a pause glyph in the free top-left corner) with the words on the hover card. A put-away chat cannot be hidden or unhidden by hand (the menu's Hide is off). Close reads "Put away" only when `isPointedMainChat` is true (strict: false while the project pointers are not loaded, so a soft word never hides a real close; `listedAsProjectMain` stays the lenient one): chat menu, row menu and Ctrl+W (`close-chat.ts` `closeVerb`/`closeIsPutAway`; no confirm dialog at all, Ctrl+W included, because nothing is deleted and the daemon waits the turn out, no death cue or exit animation, a held result shows a toast and never fires `cc:session-closed`). The pane of a put-away chat or sub is read-only (`.readonly-banner.put-away-banner`, composer disabled with its own placeholder through `readOnlyReason`) and never calls `unfreeze_session`: a put-away freeze is manual, so `selectSession` does not wake it. `syncSubchatChrome` rebuilds the pane when `dataset.putAway` flips. History needs no front-end filter: `collect_listed_history` skips open rows. A put-away chat takes nothing else from the UI either: `mainChatFor` skips it (a new-chat draft is then an ordinary chat), `nextChips` gets `putAway` (no quick-reply chips), the palette and project dashboard offer no close for the family (and say Put away for the pointed main chat), Ctrl+W on it toasts "Already put away", the idle-freeze wake in `selectSession` skips it, and the sidebar refresh never flushes its staged messages (they stay until a reopen; a background flush clears the set before the daemon's refusal). The banner and hover card count subs with work left (pausedSubs), not subs actually frozen yet. Not built here: the sub peek composer and the sub menu's Resume still offer a send to a paused sub (the daemon refuses it), the Close-and-/pickup CTA starts no new chat on a put-away main chat, the reopen door and "Continue the plan?" (step 6), and the project dashboard's live chat list still counts a put-away chat (`gather.rs` `counts_as_live`).
