# Subchats (main chat, subs, cards, decisions log)

Read before editing anything under `src-tauri/src/daemon/subchats/`, the sub rules in `lifecycle` or the hooks server, `src/views/sessions/main-chat.ts`, `sub-list.ts`, `subchat-view.ts`, `src/shared/chat/subchat-cards.ts` or `permission-modal/askers.ts`.

- **Subchats module map.** A chat with "Use subchats" on (`ChatConfig.subchats_on`) hands jobs Joe names to hidden child chats (subs), whose questions and results show in the main chat's window. Everything daemon-side lives in `src-tauri/src/daemon/subchats/`; add to it rather than spreading logic through lifecycle and hook files. `brief.rs`/`spawn.rs` decide a mode-on `spawn_chat` (required brief, the three tiers, depth 1, cap of 10 started subs (`spawn/cap.rs::started_subs`: a queued sub and a never-started row with no hold hold no slot, since the cap bounds claude processes; the cap is soft: a queued sub that starts later does not re-check it, so a main chat can pass 10 while queued subs start), a duplicate name refused); `held.rs` keeps subs the daemon holds without a child (`after`, the writer queue) and `lost_hold.rs` rebuilds the hold of a sub that never started and lost its entry; `worktree.rs` gives every writing sub (not a gate, not read-only) its own tree and branch at `.claude/worktrees/sub-<id>/tree` (Joe 2026-11-12: no project toggle; `ProjectConfig.subchat_writers` is still parsed and ignored), merged back with a rebase and `merge --ff-only --no-overwrite-ignore`, removed with its branch and its `sub-<id>/` holder (a `.cargo/config.toml` pointing cargo at `sub-<id>/target`, because the shared `D:/cargo-target` kept a ~3GB copy of our crates per tree path that nothing freed) only when merged, clean and with no unpublished submodule commit; removal runs git with `core.longpaths=true` and finishes a delete git gave up on (git stopped at node_modules paths over 260 chars after unregistering the tree, which stranded every tree of 2026-11-10/11), finishes a tree git left half removed, and `restore` retries at boot the trees `on_ended` marked closed (a `closed` file in the holder; a row that ended by an app shutdown or a dead process is never swept). `worktree_safety.rs` adds two refusals to removal: a tree holding files git ignores that the setup did not make (`status --ignored`, build output such as `target` and `node_modules` excluded, the setup's own output recorded in `<git dir>/cc-setup-ignored`) and a detached HEAD whose commits no branch or remote holds; a merge in flight is held by a `MergeGuard` that releases on drop, so a panic or a never-started merge thread cannot leave `merging()` true; `update_branch` writes a `cc-rebasing` marker before its rebase, and a rebase in progress WITH the marker (the daemon died inside it) is aborted so the land can retry, one without it (the sub's own conflict) is never touched. `build_target.rs` frees a sub's private cargo `target` (`sub-<id>/target`, kept apart from the tree so the tree can stay) when the sub finished and landed, and `restore` sweeps the targets of finished, idle subs older than 3 hours by directory mtime, logging one INFO size line; it never deletes outside `<repo>/.claude/worktrees` and never touches a row that is busy, held, queued or has a pending merge. `writers.rs` is the one-writer slot left for subs on the main checkout: a gate (a project-wide gate slot, after merges in flight) and a writer in a folder that cannot have a worktree. `finish.rs`/`turn_end.rs`/`stall.rs`/`stuck.rs`/`ceiling.rs` run a sub's end (`finish_subchat`, the Stop hook's block-nudge-card sequence, the 30-minute card, and `ceiling.rs`'s context bands (no card: Joe 2026-11-16, "stop asking me how many calls or how many tokens, if we agreed it resets at a point, reset it"; a long run alone, a call count or a size never asks Joe anything); a sub queued for the writer slot, `writers::waiting_behind`, is never blocked, nudged or carded as stalled, a turn opened by a new message starts a new block-nudge round, and Joe's failed "Nudge again" draws one "did not help" card, never the same card again); `queue_watch.rs` wakes a main chat once when a sub has waited 5 minutes with nothing in its way (its `after` finished cleanly, the slot is free, or its hold is gone), and `card_watch.rs` wakes it once when a sub's stall card (stuck, stopped, died) has gone 10 minutes without Joe's answer, so a main chat never schedules prompts to poll its subs; `plumbing.rs` is the rule that a sub's plumbing never reaches Joe as a card (Joe 2026-11-12: a sub that could not start, a worktree or bootstrap failure, a refused merge, a conflict the sub did not fix after `merge_followup` told it once, a continued branch that could not be updated): it wakes the main chat once per problem with fixed words, `subchat status` returns what failed as tool data, and the main chat fixes it with `subchat retry` (`held::retry`, start a sub whose start failed), `merge` (`merge_followup::merge_now`, land a finished sub's refused merge) or `drop` (a never-started sub, or giving up a refused merge so its commits stay on the branch), asking Joe only when it needs his decision; a merge refused because another chat has uncommitted changes in the same files raises nothing and wakes nobody: `pending_merges.rs` keeps it on disk and the busy_watchdog tick lands it (`merge_followup::retry_pending`) once those files are clean; every other refused merge is kept in the same file until it lands or is dropped, so `merge_followup::unresolved` keeps an `after` sub waiting across a restart too; a removed-worktree card on an ended sub (`worktree::on_ended`, tree kept or build folder left) is the one plumbing card left, as the record of where unmerged commits sit; `routing.rs` stamps `display_session_id` on question, permission and secret payloads so a sub's card shows in its main chat while `session_id` stays the answer target. `card_log.rs` stores the cards a sub draws in its main chat (`facts.rs` computes their chips from git and the transcript), `back.rs` queues the one line served on Joe's next message, `finish_subchat` requires `decided`, `ruled_out` and `learned` (each a list of at most 8 rows of 200 chars, `["nothing"]` is valid, a refusal names every field left out): `learned` lists what the job taught that stays true, each row naming the memory file or todo id the sub saved it to first with the save step (`~/.claude/refs/save-step.md`), is stored on `FinishRecord` and is deliberately not copied to the decisions log or the digest, `decisions.rs` keeps the decisions log (there is no "checkup" of it: that card read as noise and was removed 2026-11-12, so a finish never runs a model or raises a card), `closing.rs` holds a close that would strand running subs or unmerged worktree commits and moves a family on `respawn` or promotion, `reply.rs` is typing to a sub and "Move to sidebar", `adopt.rs` is the reverse ("Move into main chat" in the chat menu: placeholder brief, an idle child is stopped so the next send relaunches it as a sub, the main chat is woken to hand it a job), `tool.rs` is the `subchat` MCP tool, and `jsonfile.rs` keeps an unreadable state file aside as `.bad` instead of reading it as empty. **The seams:** `subchats::is_sub(&Instance)` is how any list or rule asks "is this a sub" (`subchat_of`, never `worker_of`: a sub must not wake its parent the way a Jarvis worker does); `subchats::on_finished(state, sub_id)` is the one hook a finish fires (card, one line back, decisions, `after` queue, wake); `cards::raise_card` is the only way the daemon puts its own question card in a window; `subchats::role_launch` decides on every launch whether a row is a sub, a main chat or neither. **Data files** are under `<data_dir>/subchats/`: `<main>.cards.jsonl`, `<main>.pending.jsonl`, `<main>.decisions.md`, `<sub>.finish.json`, `<sub>.digest.md`, `held[suffix].json` and `pending-merges[suffix].json` (per daemon instance: a test or dev daemon on the same data folder has its own registry, and a shared file let every `cargo test` wipe the live queue, 2026-11-10). A leftover `checkups.json` from an older build is never read. A sub that never started and lost its hold is rebuilt from its brief by `lost_hold::recover_lost` only within `RECOVER_WITHIN` (2h) of its spawn; an older one is left to the watchdog and the `subchat drop` action. **Hard rules:** a sub's text never travels inside an `is_meta` message (only as hook context framed as data, `back.rs` and the decisions rider); a sub is never `worker_of`; only the daemon writes the decisions log, so no chat carries it; every field of `held.json`'s and `pending-merges.json`'s entries except the sub id has `#[serde(default)]` and an unreadable file or entry is kept as `.bad`, never read as empty. **A project knows its main chat** (2026-11-12, D1): `ProjectConfig.main_chat_id` (`#[serde(default)]`) names the one live main chat per project. `main_pointer.rs` keeps it true to the registry: `reconcile` keeps a live pointer, replaces a dead one with the project's newest live mode-on chat and clears it when none is left, and runs from `publish_mode_changed` (every mode flip, so a menu flip and the `start_session` rollback), after `start_session` registers a new main chat (its mode is written before the row exists), from `settle_family` (every close path settles after it marks the row ended), and from `heal_orphans` at boot and on the 60 second tick; a `respawn` successor takes the pointer through `hand_over`. The daemon never writes settings.json: it sets its cache and publishes `project_main_chat_set`, which `daemon_link/handlers.rs` merges and persists. The pointer is read by the draft and the sidebar from `list_projects` (`project-main-chats.ts`, re-read on `settings-changed`, the `subchats-on-changed` nudge and at mount), and a reader always checks the chat it names is still open, since the heal can lag a crash by a minute. Closing the pointed chat always asks first (`closing::needs_approval`, `main_chat_line`): closing deletes its Answers and Ask stores (`ask/store.rs::drop_for_chat`) and ends its finished subs, and the pointer clears with it; `APPROVED` keeps the pump's EOF backstop from raising a second card for a close Joe already approved. A new chat in a project with a main chat (`draft-subchats.ts`) shows "Goes to <title>, <project>'s main chat" and a Plain chat instead switch where Use subchats sits, and sends its first message to that chat (`pending-pane-composer.ts::sendToMainChat`, a scheduled message goes there too); with Plain chat instead on the draft is an ordinary chat with the mode off. The sidebar's Main chats group lists only the pointed chat of a project (`listedAsProjectMain`); a second mode-on chat in the project draws in the group its state puts it in. With no pointer loaded (a phone whose project list failed) every mode-on chat lists as before. Frontend: `src/views/sessions/main-chat.ts` (`mainChatInfo`, `showsSubs`: the sidebar row's dots, count, hover and ring), `sub-list.ts` and `subchat-view.ts` (header count, list, reading a sub in place), `src/shared/chat/subchat-cards.ts` and `chat-subchat-card.ts` (cards and chips), `permission-modal/askers.ts` (chips for several askers in one window). What a paired machine sees: `docs/multi-machine.md`.

- **Main chat digest.** A main chat never closes, so no model turn writes its recall digest: `decisions.rs` rewrites `<data dir>/subchats/<main chat session id>.digest.md` from the chat's decisions log every time the log changes (`append_in`, the one write path every card answer and sub finish goes through, plus `move_log` on a respawn), in the same folder and four-section format as a sub's digest. Live `card` and `decided` entries become `## Decided`, `ruled_out` entries `## Rejected`, replaced entries are left out, `## Done` names the subs that reported rows, and `## Open` is `none`; a log with nothing decided or ruled out writes no file. The global `recall` tool ingests it with the sub digests, and only the daemon writes it.
- **Moving a main chat and its subs to another account** (Joe 2026-11-13, D67-D69). The Change account picker (`change-account-modal.ts::openChangeAccountForChat`, opened from the chat menu, the statusbar account chip and the rate-limit banner's Switch account) shows "Also move its N subchats", on by default, on a chat with subs that have not ended. `account-move.ts` then calls `move_session_to_account` once per chat, main first, skipping any already on the target, so a working sub restarts on the new account at once and gets "continue", the same as a single move. Subs started later copy the main chat's account, so they follow with no extra state. API credit is left out of that picker for a sub, a mode-on chat or a chat with subs, and `subchats::refusal_for_move` refuses it in the daemon too, the third door after the mode toggle and the sub spawn. The rate-limit banner never picks a target itself: an account it guessed could be the one that is not working.

- **`after` takes a list, and a sub's context reaches its main chat** (2026-11-14). `spawn_chat`'s `after` is a name or an array of names; both reach the daemon as one string, a name per line (`brief::after_names`), and `Held.after`/`after_name` hold one id and one name per line the same way, so an entry written before lists existed still reads as one target. `held::after_all` is the one verdict over them: blocked as soon as any one ended blocked (the card names that sub), clean only when all finished cleanly. `ceiling::context_pct` is the sub's context share in whole percent, shown as `context_pct` by `subchat list` and `status`; the 60 second sweep also wakes the main chat once per band at 60 and 75 (`CONTEXT_BANDS`, text from ids and a number only), and there is no 90% card any more. **Sub size (pc-1752 and pc-1754, 2026-11-16):** (1) a sub compacts itself: `lifecycle/spawn.rs` sets `CLAUDE_CODE_AUTO_COMPACT_WINDOW=300000` on a sub's child (spiked on claude 2.1.325: the CLI compacted twice inside one turn, which the daemon's turn-end compaction cannot do for a sub whose growth is one long turn); `compaction::session_start_answer` then hands a compacted sub its brief word for word, `git status`, `diff --stat` and its own decisions rows (`sub_session_start_context`, hook context, never message text); a compaction mid-turn raises no stall and no nudge since no turn ends. (2) `subchat send` refuses a writing send, or any send after the finish, to a sub at or past the first band (`ceiling::heavy_send_refusal`, `ok:false` naming `continue_from`); a question inside a running round still goes through. (3) `spawn_chat` `continue_from: <sub name>` (idle or finished writing sub of the same main chat, here, no `after`): `worktree::plan_continue` commits the old tree's uncommitted work as a WIP commit and `prepare_at` starts the new tree from that commit; once the new sub is registered `worktree::hand_over` detaches the old row's tree, ends it and removes its tree and branch against the successor's branch (every commit is on it, the usual clean and no-ignored-work checks still apply); the new first message names the old sub by id and sanitised name only. (4) The decisions log shows a sub Joe's card answers, rows starting `rule:` (a convention for the whole project, at most 3) and its own rows; another sub's `decided` and `ruled_out` rows stay in the file but are not injected (`decisions::visible_to`), and a sub's `replaces` row never closes a card answer. (5) The stuck sweep raises one card per turn (`runtime::stuck_carded_gen`), so a sub that waits on purpose does not wake the main chat every half hour; UNVERIFIED which stall kind produced the 2026-11-14 repeats, the app log from that day is gone (the log keeps one file, `Claude Conductor.log`). A sub closed from the UI goes through `end_sub` (`mark_session_ended`), the same end as the daemon's "End it". A target that read as finished cleanly goes on `Held.cleared` (`#[serde(default)]`) and later checks skip it once it has ended (one that went back to work is read again), so closing a merged sub while a sibling target still runs raises no "ended before it finished" card; a target closed before it read clean (a refused merge dropped by the close) still counts as blocked. A scheduled new chat the start cap refuses (`SPAWN_CAPPED:<secs>`) is requeued like a rate-limited one.

- **A sub's answers and drafts reach its main chat** (2026-11-15). `hooks_server/messages/mod.rs::draw_sub_card` draws a sub's `send_message` of kind `blocker`, `answer` or `rating` into the main chat through `card_log.rs` (`on_blocker`, `on_answer`); every other kind (report, plan, progress) stays in the sub. An answer card keeps the whole message: `text`, `points`, `details` (`CardEntry.details`, so the `[label](#d:id)` links open), `visuals`, and its `question`, which is the one the send carried or else the brief's pending one, spent from the brief at once so the sub's later finish is not a second answer to it. `update_message` from the sub rewrites or retracts the card it drew in the same turn (`on_answer_update`, remembered per sub and turn gen in `TURN_ANSWER`; the daemon never learns the ordinal `update_message` counts by, so an update of an older turn's message is not mirrored) and announces it again as a `subchat_card` frame with `replace: true`, which `ChatRenderer.onSubCardFrame` swaps in place. The Messages view tags the card with the sub's name (`renderSubCard`); the Answers card counts it through `answers-model.ts::isSubAnswer` (`kind` answer or rating, question optional, filling that sub's pending hand-off row at once). A sub's `write_draft` stamps `MessageDraft.origin_main_session_id` (its `subchat_of`, `#[serde(default)]`; `closing::move_family` rewrites it on a `respawn` with `message_drafts::rehome_main`), and the dashboard's Drafts card (`drafts-model.ts`) lists a draft when that field names this chat or, for one written before the field existed, when its `origin_session_id` is a live sub or a sub of the card log (a closed sub's drafts still list), each labelled `from <sub name>`. The sub prompt (`claude_config/args.rs` `SUBCHAT_SUB_PROMPT`) tells the sub which kinds reach the window.

- **Cross-machine subs** (a main chat here, its sub on a paired machine): design, trust rules, wire and build steps in `docs/cross-machine-subchats.md`. Read it before touching `subchats/remote/` or any sub path that runs on a sub's host instead of its main chat's daemon. A visiting sub's `send_message` cards (`blocker`, `answer`, `rating`) never draw on the host: `card_log::on_blocker`/`on_answer` queue an `Event::Card` and the home draws it (`draw_remote_card_at`); Joe's answer to its question is logged on the home only (`decisions::record_remote_card_answer`, called by `machines/forward.rs`), and `card_ctx` writes nothing for a visiting sub. `scripts/cross-machine-verify.mjs` is the two-daemon live run.

- **Is the main chat still there** (2026-11-15). Every sweep that drops or settles subs because their main chat is gone (`held::orphaned`, `closing::heal_orphans`, `queue_watch`) asks `held::chat_live`: the chat's row is open, or the daemon holds its child. A row alone is not enough, because a row can stay `ended_at` while the chat runs again (a SessionEnd hook closed an External row, then a scheduled wake resumed it, and the sub it spawned next was dropped with its half-set-up worktree). `schedule_fire::reopen_ended_row` reopens such a row after a wake, and a launch whose sub ended during its worktree setup stops with `held::ENDED_BEFORE_START` and tells nobody. `held::release` logs its caller, so a hold that vanishes is traceable. `subchat status` and `list` read a sub that ended its turn to wait on its own background job (`Instance.local_task_running`) as working, progress "waiting on its background task".

- **Autopilot picks** (pc-1750, `daemon/subchats/picks.rs`, `hooks_server/autopilot_pick.rs`, `methods/picks.rs`, `mcp/tool_schemas_picks.rs`). A choice with real alternatives that an unattended run made because nobody could answer a card is recorded by the `autopilot_pick` tool, never inferred from `finish_subchat.decided` (pc-1663: those rows are mostly status facts). The tool is listed for every chat (the list is fixed at process start), so the gate is the route: a chat is unattended when it or its main chat has `Instance.autopilot` (the `<cc-autopilot:on>` marker), and an attended call is refused naming the question card, so an attended choice never reaches the list. Store: `<data_dir>/subchats/<owner>.picks.json` (owner = the main chat, `owner_of`), every field but `id` `#[serde(default)]`, an unreadable file kept as `.bad`. Each pick of a mode-on chat also writes one plain `Decided` line into the decisions log, and an overrule closes that line with a `replaces` entry; a typed row inside the markdown log was rejected because its entries are append-and-close and a pick's review status changes. Joe reviews on the chat dashboard's Autopilot picks card (`picks-card.ts`, desktop pipe only: `picks_state` and `picks_review` are absent from the transport table): Agree, or Overrule with what he wants instead, which sends the correction to the main chat as his message; the chat changes the code and calls `autopilot_pick` with `action: "corrected"`. The daemon publishes `autopilot_picks_changed` (`{session_id, unreviewed}`, never a pick's text) and the card re-reads.
- **A sub's tree is removed when it is merged and clean, and the submodule commits only it holds are saved first** (2026-11-16, `worktree/removal.rs` and `worktree/removal/module_keep.rs`). A worktree's submodules keep their git dirs inside the worktree's own, and `git worktree remove` refuses any tree with an initialised one, so the removal ends in `--force`, which deletes them. Before that, `keep_modules` fetches the tip of every module's HEAD, local branches, tags and every stash entry that holds a commit no `refs/remotes` ref has, and every commit the tree's own parent recorded for the module (its index entry and the last 200 commits that touched it) that no remote has, into the MAIN CHECKOUT's copy of the module (`repo/<path>`) as `refs/cc-sub-kept/<sub id>/<n>`, reads each ref back, and only then lets the removal go on: a merged, clean tree is never kept just because its module has unpublished commits, and Joe gets no card for it. A module pointer the tree moved to a commit the branch never recorded shows as ` M <path>` in the parent's status; `drifted_modules` keeps that out of "uncommitted work", and the commit it points at is saved even when a remote has it, because the parent's record of it goes with the tree. Still kept, with a card: a tree whose submodules `git submodule status --recursive` cannot list, a module with uncommitted work (checked in every module before anything is saved, so a kept tree is left as it was apart from a scratch ref `refs/cc-sub-keep-src/<n>` inside the module's own git dir), one that cannot be checked, one the main checkout never set up (no `.git` in `repo/<path>`, so there is nowhere to save), and a failed or unverified save. Recover a kept commit with `git -C <main checkout>/<path> branch <name> refs/cc-sub-kept/<sub id>/<n>`; nothing prunes these refs. The rule line in CLAUDE.md ("removed only when merged, clean and with no unpublished submodule commit") should now read "removed only when merged and clean; a submodule commit no remote has is saved first under `refs/cc-sub-kept/` in the main checkout's module, and the tree stays only when that save is impossible".
- **A `blocker` card is only for something Joe must act on** (2026-11-16, Joe: "what am I meant to do here, why did this even get shown to me" about a red "Merged / Its commits are now in master."). A `blocker` card in the main chat's log lands in the dashboard's Waiting on you zone in red until its sub sends a later card, so the daemon draws one only when there is a decision for Joe. Audit of every source: (1) a sub's own `send_message` blocker (`hooks_server/messages::draw_sub_card`) is KEPT, it is the sub's word; (2) `worktree::on_ended`, a tree kept because it holds work (`worktree::keeps_work`: unmerged commits, uncommitted or git-ignored files, a detached HEAD, a submodule's work) is KEPT and says what to do ("Tell this chat to commit and merge that work, or delete the folder by hand"); (3) `worktree::on_moved` when the merge was refused is KEPT, with "tell it to resolve this and merge the branch"; (4) `on_ended` for a tree the app did not make, a delete git or the OS left half done, or a leftover build folder (`Removal::BuildLeft`) is now the APP LOG only (`keeps_work` lists these housekeeping reasons, so a new reason defaults to a card); (5) `on_moved` that merged or had nothing to merge is the APP LOG only; (6) `merge_followup::merge_again` after a successful `subchat merge` or tick retry draws NOTHING, the app log has the fact; (7) every `plumbing::report`/`report_here` source (could not start, conflict, merge refused, not up to date, not rebuilt) stays a wake of the main chat and never a card. The app's own blocker cards carry `CardEntry.by_app` (`card_log::on_app_blocker`, `on_app_blocker_for`); a sub's own `send_message` blocker never does. A landing or any other `plumbing::resolved` calls `card_log::retract_blockers`, which marks only the `by_app` blocker cards of that sub `retracted` in the log and announces them with `replace: true`, so the dashboard's `subBlockerLive` drops them; a sub's own blocker is its word and a landing says nothing about it. Only a LOCAL sub's cards are retracted (a visiting sub's cards are drawn on its home, which has no `resolved` for them). A blocker never keeps tone `good` (`card_log::blocker_in` drops it), because the dashboard reads that tone as a success notice (`dashboard/blocker-notice.ts::isGoodNews`, which also drops the verdicts "Moved with its worktree" and "Build folder left" that older builds drew), so cards an older build wrote stay out of Waiting on you. Old red "Worktree kept" cards for housekeeping reasons stay until their sub sends a card; Joe removes them with the x or Clear all. Known gap: a tree that is not registered with git any more but still holds files is classed as "not a worktree this app made" (housekeeping, app log only) even though the files might hold work.
