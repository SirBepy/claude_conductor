# Phone link (Android tunnel, stream heartbeats, journals)

Read before editing `android/src-tauri/src/iroh_tunnel.rs`, `journal.rs`, `android/src/app.js`, `daemon/remote_ws_pump.rs`, `remote_send_dedupe.rs`, `methods/link_journal.rs`, `global-stream.ts`, `http-transport.ts`, `connection-state.ts` or `link-journal.ts`.

- **Phone link module map (2026-11-12).** How the Android app stays connected, and where to read what happened. **Tunnel** (`android/src-tauri/src/iroh_tunnel.rs`): one shared QUIC connection per PC, dialed under the `Slot` lock. A failed dial is shared with every caller that queued behind it; a lost connection (wake-up, close, invalidation, failed call) sets `needs_fresh_endpoint`, so the next dial binds a fresh endpoint FIRST and falls back to the old one only if the bind fails; at most one rebind per call, the second attempt stays on that endpoint with `RETRY_ATTEMPT_TIMEOUT`; `watch_for_stop` abandons a dial the process slept through (wall clock, `STOP_GAP`); `last_alive` is stamped on every exit of `connection()`. Beside it, `tunnel_ports.rs` holds the port scheme and loopback binds, `quiet_watch.rs` the received-traffic watch, `forward.rs` the loopback request handling and journal serving, and `test_support.rs` the shared test helpers. The watchdog (2s) also counts ticks with no received datagram while a stream is open (`quiet_step`, in `quiet_watch.rs`): `network_change()` at `QUIET_NUDGE` (8s), drop at `QUIET_DEAD` (12s). That watch only sees the downlink, so a second one judges the uplink (`uplink_step`, journal `unacked` at `UPLINK_NUDGE` 4s, `uplink_dead` at `UPLINK_DEAD` 8s, each journaled with `paths=[...]`, `*` on the path QUIC sends on): while a stream is open and the connection has sent ack-eliciting frames (`frame_tx.stream + ping`), the PC's ACK counter (`frame_rx.acks + path_acks`) must move; datagrams that keep arriving (the PC's own PINGs and heartbeats) do not count, and a connection that sends nothing never waits (an idle one receives no ACKs). Added after the 2026-11-13/14 journal showed 30-57s windows where every request went silent on a connection that had just dialed fine and whose global stream had opened, with no `quiet`; UNVERIFIED that the uplink is the cause, which is why `forward.rs` also journals `stream_slow after=5s open=N rx= sent= acked= lost= id=` (`id` is the connection's `stable_id`; the counters are those of the connection cached at the 5s mark, so a changed `id` between two lines means a redial happened in between) for any request unanswered after 5s (rx and acked both moving means the PC got the request and has not answered; acked flat with sent moving is the uplink). The QUIC idle timeout stays 30s on purpose (iroh rides out relay reconnects; a shorter one was reviewed and rejected). The journal (`journal.rs`) is served on its own loopback port, the tunnel port + 1, with CORS for the tunnel's origin only, and never dials; the page must not read it from its own origin, because the WebView reuses kept-alive connections that are already spliced to the PC (`forward()` still answers `GET /__tunnel/journal` on a fresh connection). It holds 200 events ( `bind`/`rebind` with the first 8 hex of the phone's endpoint id, `dial_ok ms=`, `dial_fail`, `resume`, `slept`, `tick_late`, `quiet`, `dead`, `drop`). `probe_iroh_tunnel` dials before `android/src/app.js` leaves the shell. **Daemon**: a session stream opened with `?hb=1` gets the heartbeat frame every `GLOBAL_HEARTBEAT_INTERVAL` from all three pumps and during `wait_for_respawn`, never without it (a paired machine's relay passes every frame on as a chat event); the global stream answers `{"method":"ping"}` with a heartbeat and resends the instances snapshot on `Lagged` (`remote_ws_pump.rs`). `POST /api/sessions/:id/send` runs detached from the request (`run_detached`: a dropped request used to leave `busy` latched until the 20-minute sweep) and dedupes on `client_msg_id` (`remote_send_dedupe.rs`, memory only, success only, 30 min). `IrohTunnel::close()` runs on the daemon's normal exit so clients get a close frame. `report_link_journal` (`methods/link_journal.rs`, mask `P`) writes `[phone-link] dev=<device> <line>` into `daemon.log`; stream opens and closes log `[remote-ws] dev=<device> kind=<phone|peer> ...`. **Page** (phone transport only): `global-stream.ts` pings a stale-looking open socket on resume instead of dropping it; the per-chat branch of `HttpTransport.listen` has its own watchdog (`CHAT_STREAM_STALE_MS`, acts only once a heartbeat was seen) and sends a synthetic `events_lagged` on every reopen; `wireChatRecoveryHeartbeat` keeps the 15s revive for the desktop only (phone: 60s visible-only re-read, one pass on resume); `BACKGROUND_READS` in `connection-state.ts` lists the methods only ever polled, which must never raise the "Waiting for your PC" strip; a method the user also waits on (`list_instances`, `get_session_drafts`) is not listed and its pollers pass `{ background: true }` (`CallOptions` in `transport.ts`); question, permission and secret cards arrive as `question_request` / `permission_request` / `secret_request` / `question_expired` frames on the global stream (`GLOBAL_EVENT_MAP`, `startPromptFeed` in `permission-modal/remote-prompt-poll.ts`), with `list_pending_prompts` read on every stream (re)open (`onGlobalStreamOpen`) and on a 3.5s fallback poll that stays inside the daemon's 8s render-confirm window (a prompt answered on the desktop has no frame and leaves through that poll); `isAndroidShell()` (`window.ConductorPush`) pauses that poll while hidden; a page left open across a PC update reloads once onto the new build: the daemon stamps `<meta name="cc-build">` (a hash of the embedded index.html) into the pages it serves and reports the same id as `build` in `/api/health`, and `build-check.ts` compares them on every stream open, deferring while any message box holds text and guarding a loop with a sessionStorage stamp; a missing `/assets/*` file is a 404 (`remote_static.rs`), never index.html; `link-journal.ts` records page events and uploads them with the tunnel's. Reading the journal: a `strip_show` and `strip_hide` within a few ms of `visible` was never drawn (both run in the one visibilitychange task); only a `strip_show` that stays until a later `strip_hide` was on screen, and the strip changing from "Waiting" to "Reconnecting" is not journaled. Events from a stretch with no link only reach `daemon.log` after the link returns, so a missing `t` line in a dead stretch proves nothing; the tunnel's ring dies with the process. A stable tunnel id in `iroh tunnel: connection from <id>` lines is the paired Mac's dialer (one ephemeral key per process), a changing one is the phone (random key per bind). Scratch analysis scripts for that log: `.for_bepy/phone-disconnect/`.
- **Chat list on the global stream (2026-11-16).** The page opens `/api/global/stream` with `delta=1`. The daemon then sends one whole `instances_changed` list per connection and afterwards `instances_delta` frames with only the rows that differ from what that socket was last sent (`InstancesDelta` in `remote_ws_pump.rs`); a list whose rows were added, removed or reordered goes out whole, an unchanged one not at all. A stream opened without `delta=1` (a paired machine, an older page) gets whole lists as before. The page keeps the list (`streamedInstances` in `global-stream.ts`) and `HttpTransport` answers `list_instances` from it while the socket is open, so a change frame costs no request. Why: every registry mutation publishes the whole list, measured at 177 rows and 190KB, 9 times in 30s with one changed row each, and the page fetched the list again per frame; a relay link measured at about 20KB/s on a hotspot then queued every other request 13s and more (0.24s with the PC quiet), which the page showed as "Waiting for your PC" and "Reconnecting". Never add a per-frame refetch of a large read to a global-stream listener.
- **A sent message never returns to the composer (2026-11-20).** The daemon holds a copy of the composer text (`draft_store`) that a reopened page reconciles into its box. The phone's clear of that copy (`clear_composer_draft`) is its own request, so a page suspended right after Send never sent it, and the typed-text write (`set_composer_draft`) could overtake it, which left the sent text as the newest draft. The daemon now retires the draft itself: the REST send route calls `DraftStore::note_sent` on an accepted send, which tombstones the draft when it still equals the sent text (trimmed) and remembers that text for 30s so a typed-text write landing after the send (`set_composer_at`) is dropped. Never make the page's own clear the only thing that retires a sent draft. Ruled out: a page-side guard that matches a remote draft against the sent outbox (it wipes a real draft that repeats an earlier message such as "continue"), and queueing the page's daemon writes (one hung write blocks every later clear for the 120s mutation timeout). A message staged into the held queue while the chat is mid-turn (`add_held`) retires its draft the same way. A mirrored chat's draft lives on its owner, so the owner's own `send_message` RPC (`lifecycle/core.rs`, which the desktop's sends also pass) does the same call and the REST route skips it for a session it does not own. The memory ends at the first different write. Known gaps: a send whose text differs from the box (pasted-block placeholders) matches no draft; an earlier intermediate write ("ship i") that lands after the send is not the sent text and is kept; a write delayed past 30s is kept; a held-queue flush that bundles several held items with the draft sends text that is not the draft, so the draft is kept. The same words put back into the box in one step inside the 30s (a quick-reply chip, dictation) are dropped on the daemon only: the page keeps them in its own storage, the other surface just does not get them. No test drives the two call sites end to end (a local session needs a live child); only the store's tests pin the behaviour.
- **The page's first load after a PC update is the slow part (2026-11-24).** Every release renames the hashed bundle files, so the phone's service worker has nothing cached for them and the whole boot path comes over the tunnel: `index.html`, `main-*.css`, `main-*.js` and `print-block-*` are 2.0 MB raw, 0.57 MB gzipped, and nothing paints until the stylesheet lands, and `index.html` opens the page after 3s anyway (its `app-ready` timer, meant for a broken build) so a bundle still downloading shows as the bare, unstyled markup, a white box, never the app. Over a relay path measured at about 20KB/s that is 100s raw against 30s gzipped, and the tunnel's own watches (`QUIET_DEAD` 12s, the 30s idle timeout) drop a connection that stalls that long: the daemon log showed 36-52s phone connections after the 0.2.159 update with no `[remote-ws] kind=phone global open`. `remote_static.rs` therefore gzips text files for a client that sends `Accept-Encoding: gzip` (hashed files compressed once and kept in memory) and marks `/assets/*` `Cache-Control: immutable`. Never serve the bundle uncompressed again, and keep the entry chunk small: a bigger boot path costs a phone on a poor link that many more seconds on the first open after every update. UNVERIFIED on the phone itself: nobody read the phone's own journal for the failed opens, so link speed as the cause rests on the daemon log and the byte counts.
