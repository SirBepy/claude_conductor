# Endpoint accounts (third-party model providers)

Read before editing `src-tauri/src/accounts/endpoint.rs`, `src-tauri/src/ipc/endpoint.rs` or the Endpoint branch of `src-tauri/src/daemon/lifecycle/spawn.rs`.

- **What it is.** `AccountKind::Endpoint` runs the `claude` CLI against a third-party Anthropic-compatible endpoint (Kimi Code, DeepSeek, OpenRouter, a custom URL) with that provider's key. The CLI stays the harness; only the model behind it changes. It has no OAuth login, no claude.ai cookie and no Console login, so everything that reads those skips it (usage poll `scheduler::account_has_cookie`, `get_auth_state_map`, the drift and credentials checks in `spawn.rs`, the model probe `ipc/models/config_dir.rs`, re-auth and cookie recapture in `ipc/accounts/identity.rs`, claude.ai connectors).
- **Config.** `Account.endpoint: Option<EndpointConfig>` (`#[serde(default)]` everywhere): `preset` (`kimi_code`, `deepseek`, `openrouter`, `custom`; a label only, spawns never read it), `base_url`, `auth_style` (`bearer` or `x_api_key`), `models` (ids for the picker, each passing `is_valid_endpoint_model`). An old `accounts.json` entry loads as a Subscription account with `endpoint: null`.
- **The key** is stored exactly like an API-credit key: a DPAPI-wrapped `apikey-<id>.txt` in the data dir through `accounts::api_credit::{save_api_key, load_api_key}`. Never in `accounts.json`, never in a log (`SpawnEnv`'s `Debug` redacts both `ANTHROPIC_API_KEY` and `ANTHROPIC_AUTH_TOKEN`). The key is not checked against the provider when added: each vendor's check differs, so a wrong key shows at the first turn.
- **The spawn env** (`SpawnEnv::for_endpoint_account`): everything `for_account` does (OAuth token, API key and auth token scrubbed), then `ANTHROPIC_BASE_URL`; bearer sets `ANTHROPIC_AUTH_TOKEN` and holds `ANTHROPIC_API_KEY` at the empty string, x-api-key sets `ANTHROPIC_API_KEY` and leaves the token unset; and `ANTHROPIC_DEFAULT_{OPUS,SONNET,HAIKU,FABLE}_MODEL` plus `CLAUDE_CODE_SUBAGENT_MODEL` all pinned to the chat's model id, so a helper the chat starts inside itself stays on the endpoint. **Never set or override a User-Agent**: the CLI sends `claude-cli/...` and Kimi Code's terms forbid changing it.
- **Guards.**
  - `chat/billing.rs` `check_metered_billing_endpoint` allows `ANTHROPIC_API_KEY` and `ANTHROPIC_AUTH_TOKEN` for this kind only; Bedrock and Vertex still refuse.
  - Model ids: `lifecycle::is_valid_model_for` takes any id matching `^[A-Za-z0-9._:/~\[\]-]{1,128}$` for an Endpoint account (plus: no leading `-`, so an id never reads as a CLI flag). Claude accounts keep the family check.
  - Voice, Ask, publishing and the model probe refuse it (`accounts::refuse_non_subscription`, `config_dir_from_resolution`).
  - Unlike API credit, an Endpoint account may be the default, a project binding, a sub's account and (opt-in `fleet_eligible`) a fleet worker.
  - **No client-repo guard.** Decided 2026-11-23: an Endpoint account is not refused by project. `ProjectConfig.payment_group: Option<String>` (`#[serde(default)]`; `"personal"` or `"client"`, `None` reads as personal) is stored only and nothing reads it yet; pc-1833 phase 1b uses it to pick a routing profile.
- **IPC** (desktop-process Tauri commands, like `add_api_credit_account`): `add_endpoint_account`, `update_endpoint_account`, `replace_endpoint_key`; removal is the ordinary `remove_account`, which deletes the key file. None is a daemon method and none has a `TRANSPORT_TABLE` row, so the key cannot cross a remote transport; `list_accounts` (P) carries the base URL and models but never the key.
- **Verified CLI behaviour** (claude CLI 2.1.325, fake local endpoint, 2026-11-23, no real calls): `ANTHROPIC_BASE_URL` is honoured and the request goes to `POST /v1/messages?beta=true`; `--model <any id>` reaches the endpoint unchanged (an unknown id only prints `[claude-code:unrecognized_model]` to stderr); with `ANTHROPIC_AUTH_TOKEN` set and `ANTHROPIC_API_KEY=""` auth is `Authorization: Bearer` with no `x-api-key`; `ANTHROPIC_DEFAULT_<TIER>_MODEL` remaps that alias; a `[1m]` suffix is stripped from the id and adds the `context-1m` beta header.
- **UNVERIFIED until a real key is tried:** each preset's base URL, auth style and model ids (Kimi Code `https://api.kimi.ai/coding/`, DeepSeek `https://api.deepseek.com/anthropic`, OpenRouter `https://openrouter.ai/api`), that OpenRouter wants the bearer style, and how each vendor's server-side cache and usage reporting behave.
- **Context window and the context %** (read before editing `context_status.rs`, `EndpointConfig::context_window` or the window vars in `SpawnEnv::for_endpoint_account`).
  - **Why it needs the account.** The CLI writes the alias it was given as the transcript's model (`sonnet`, pinned to the provider's id by the model pins above), so the name heuristic read a real Kimi chat (transcript 2026-11-24, 311 turns, last turn 199,493 tokens, model `sonnet`) as a full 200K Claude window: 100%. Kimi's window is 262,144, which is 76%.
  - **One path.** `WindowHint` (`for_account`, `for_session`, `for_instance`) is resolved from the chat's account and the model it was started with, then `ContextStatus::with_hint` replaces the heuristic. `context_status_for_session` (daemon), the app's `context_status` command (`context_status/commands.rs`), the context-cap view and the sub ceiling all apply it; a new reader of a transcript's context must too.
  - **Table** (`EndpointConfig::context_window`): `kimi_code` is 262,144; a chat whose model ends in `[1m]` has no verified window (the Kimi 1M figure from the research preview is UNVERIFIED against a real key), so it is unknown like the presets below. `deepseek`, `openrouter` and `custom` have no checked figure, so the window is unknown: `ContextStatus.window_known` is false, `window`/`pct_used` are 0 and every surface (`ctxPctOf`, `contextChipHtml`) shows the token count with no percent. Adding a provider's figure means a row in that match, never a guess.
  - **Spawn env.** A stated window sets `CLAUDE_CODE_MAX_CONTEXT_TOKENS` and `CLAUDE_CODE_AUTO_COMPACT_WINDOW` to it (`ENDPOINT_WINDOW_ENVS`). Both names are in Anthropic's Claude Code env-var reference (fetched 2026-11-24: the compact-window row verbatim, the max-context row from a summarised fetch). Kimi's own guide could not be read (a JavaScript-rendered page), so that it sets them, and that compacting at the full window leaves enough headroom, are UNVERIFIED until a real-key run. A sub's 300K compact window is capped at the account's own (`sub_auto_compact_env`), or a 262K chat would overflow before compacting.
- **Settings UI.** One page, Settings > Accounts & models (route `settings-accounts`, root class `view-settings-models-providers` kept for the mp-* CSS and `role-override-sheet.ts`), with two tabs: **Accounts** (a section per company: Anthropic holds plan accounts, API-credit accounts and the Terminal row; Kimi Code, DeepSeek, OpenRouter and Custom hold their Endpoint accounts; a dim Codex row) and **Who does what** (the routing table, lazy-mounted on first open by `mountWhoDoesWhat`). An empty company is a dashed Add row that is its own add flow; a company with accounts gets a small Add button in its header. Anthropic's Add asks plan or API credit (`add-account-flow.ts`); every other company opens `openAddEndpointModal(preset)` in `provider-modals.ts`. The phone shows the Anthropic section only: no tabs, no Endpoint rows, no add-Endpoint, no Who tab. API keys (tracker tokens) are a separate Settings page (`settings-api-keys`, desktop only), never a tab here. The page header has no info button, only the popup's close.
- **Who does what rows.** One row per kind (`role-cards.ts` `cardHtml`): the kind, what it runs on (account badge, model, account) and the effort bars. Names wrap, never cut. The bars are one per rung of the rule's own account ladder (`effortFill` in `shared/routing-rules.ts`: five for Claude and the default, three for an Endpoint), so the top rung always draws full bars; an unset effort or one off the ladder draws the label alone. What happens at the limit ("Waits at limit" / "Then <account>") and the "Main chat can adjust" flag (title: the model and effort range the main chat may move within) are small chips beside the value (`.mp-then`, full sentence in the title), never a line of their own; a Claude model on a row also carries its level on the Haiku-Sonnet-Opus-Fable ladder (`levelHtml`, battery glyph and "3/4", the same ranks as the chat battery in `sidebar-row-visuals.ts`), and the role sheet's model picker names it too; an Endpoint model has no known rank and shows none; a default row has none. A default row has no fallback; given `defaultSpec(settings, accounts)` it names what the kind runs on today, by kind class (`defaultFor`): a chat kind (`main_chat`, `new_chat`) reads Settings' `default_account_id`, `defaultModel` and `defaultEffort` as "Default · <account>" with the model and effort bars (an Endpoint default account shows "Default model", since a rule-less spawn passes the Claude family, not the provider's first model); a job kind reads the sub tier default (Sonnet, medium, a gate high) on "its main chat's account", because `route_sub` never reads Settings' default model and takes the caller's account first. (When that main chat runs on an Endpoint account the sub takes the account's first model, which this page cannot know, so the row still says Sonnet. The chat-kind effort falls back to "high" when Settings sets none, as the new-chat picker does; `spawn_chat`'s own fallback is "medium".) A project's own account or defaults, and a caller's own account, still beat the chat-kind line at spawn. Without a `DefaultSpec` (project override rows) it reads "Same as today".
- **Billing labels** live in `shared/provider-meta.ts` (`BILLING`, `billChipHtml`, `billedAsHtml`), exactly three and shown on every row and add flow: **Subscription** (a flat fee, limits set by the provider: Claude plans and Kimi Code), **Included credit** (the Max plan's monthly API credit), **Pay per token** (DeepSeek, OpenRouter, Custom). There is no "Membership" or "Plan limits" label.
- **Not here yet:** Codex (phase 4); fallback at a usage limit landed in phase 3. Usage figures are in "Provider usage" below.

## Endpoint chat trim (token plan steps 1 to 5)

Read before editing `daemon/claude_config/endpoint_trim.rs` or the `endpoint` branches of `daemon/lifecycle/spawn.rs`.

- **Why.** A small provider plan (Kimi Code) burns on the fixed prefix every call re-sends (measured 2026-11-24 on a Kimi chat: 40.8K tokens before the first word, of which CLI tools 12K, CLI prompt 8K, MEMORY.md 5.9K, CLAUDE.md files 9.6K, skills 3K) and on a long context (calls over 150K of context carried 61% of a week's tokens). Only an `AccountKind::Endpoint` chat is trimmed; a Claude chat's argv, env and `--settings` are byte for byte what they were (`claude_accounts_get_no_trim` and `an_endpoint_chat_main_or_sub_compacts_at_120k_and_a_claude_chat_is_unchanged`).
- **Step 1, denied tools.** `ENDPOINT_DENIED_TOOLS` (`Workflow`, `ScheduleWakeup`, `ReportFindings`, `ListAgents`) is appended to the one `--disallowedTools` value `base_claude_args` sets (`AskUserQuestion`), space-separated, never as a second flag (whether the CLI keeps the first of a repeated flag is unverified). `Agent` stays: subs and reviewers need it. No `mcp__cc_conductor__*` tool is ever denied.
- **Step 2, compact at 120K.** Every Endpoint chat, main or sub, gets `CLAUDE_CODE_AUTO_COMPACT_WINDOW` = the lower of 120,000 and its account's own stated window (`endpoint_trim::compact_window`, `spawn.rs` `auto_compact_env`). It replaces the sub's 300K for this kind and the account env's full-window value (Kimi's 262,144). The context % still reads the real window.
- **Step 3, lean skills.** `--settings` for an Endpoint chat lists every user skill `name-only` (the description is dropped, `/commit` and the rest still run when named) and switches every plugin off through `enabledPlugins` (`skillOverrides` has no effect on plugin skills). A project's own skill scope (`slash::scope::chat_settings`) is laid over it, so a skill scoped `off` stays off and a plugin scoped into the project stays on. Project skills and user commands are untouched. The skills dirs are read at spawn, for an Endpoint chat only. Joe's own plugin commands are unavailable in an Endpoint chat; name the skill to run it.
- **Known edges.** A `skillOverrides: {x: "off"}` Joe wrote in his own `~/.claude/settings.json` is turned to `name-only` for an Endpoint chat (only the project scope is laid back over the lean listing; his settings.json has none today). An Endpoint sub compacts at 120K, about 46% of Kimi's 262K window, so the 60% and 75% sub context bands in `subchats/ceiling.rs` never fire for it. `claude_config::chat_args` is the one argv builder, and `broker_gate0_tests.rs` scans `spawn.rs` for that single call.
- **Step 4, SKIPPED, waits on Joe.** Endpoint chats writing no memory (auto-memory off) is not built. The one-line change would be `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1` (UNVERIFIED env name, check the CLI's env-var reference first) set beside the compact window in `spawn.rs`'s Endpoint branch, with its own test.
- **Step 5, what stays.** The global and project CLAUDE.md (they carry the commit and safety rules), the `Agent` tool, the billing guard and the ask channel are not trimmed, and the `cc_conductor` tool schemas stay deferred as they are: deferring more costs more ToolSearch calls than it saves schema, so none is made non-deferred. `the_deny_list_never_names_agent_or_the_conductor_tools` pins the tool half.
- **Savings are modelled, not measured:** no billed run was made. Skills: the 3K measured listing drops to roughly the names; the other three levers have no per-piece measurement.

## Routing rules (pc-1833 phase 1b)

Read before editing `src-tauri/src/routing/`, `daemon/subchats/spawn/route.rs`, `daemon/methods/spawn_chat/route.rs` or `route_fired` in `daemon/schedule_fire.rs`.

- **Data.** `Settings.routing.groups`: payment group id -> kind -> `RouteRule { account_id, model, effort, fallback, range }` (`types/routing.rs`, every field optional and `#[serde(default)]`). Groups are a map (`personal`, `client`, more later); a project picks one with `ProjectConfig.payment_group` (`None` reads as `personal`), and `ProjectConfig.routing_overrides` (kind -> rule) beats the group's rule for that kind. `fallback` (`{"kind":"account","account_id":..}` or `{"kind":"wait"}`) is read at spawn time (see Fallback at a limit). The settings sync classifies `routing` as machine-local (`settings/sync.rs`), since rules name this machine's account ids.
- **Kinds are plain strings** (`routing::KNOWN_KINDS` lists today's: main_chat, new_chat, talk, plan, build, review, release, fix, gate, test, triage, research, errand). Never a closed enum: the Plan card's shared kinds table replaces the list later, and a kind with no rule resolves like today.
- **Resolver** `routing::resolve(settings, project, accounts, kind, base_account_id, Explicit{..})`, pure. Each field resolves on its own: explicit pick, then the project override, then the group rule, else `None` (the caller applies today's behaviour: `resolve_model_effort`, the caller's own account, the tier defaults). A rule naming a deleted account, or an API-credit account (never routable), falls through with a `[routing]` warn line. A rule's model must pass `is_valid_model_for` the account it runs on (the rule's account, else `base_account_id`), a rule's effort must be a known effort, else both fall through. An Endpoint account with no model decided gets its own first model, never a Claude tier. An explicit model not in the model list of an Endpoint account a RULE picked is dropped with a note (a Claude tier would reach the provider as an unknown id); an empty list serves any id.
- **Range.** The first of override and group rule that has a `range` clamps the EXPLICIT model and effort only (a rule's own choice is never clamped). Claude models order haiku < sonnet < opus < fable, efforts low < medium < high < xhigh < max, an Endpoint account's models by list position. A model or bound that cannot be ranked is left alone, and a range whose minimum is above its maximum is ignored. A clamp adds a note.
- **Wiring.**
  - Plain `spawn_chat` and `respawn`: `spawn_chat_routed` -> `route_plain`. Kind `new_chat`, or `main_chat` for a `respawn` of a subchats-mode chat (the successor stays a main chat); a respawn counts its own model and effort as explicit, so a rule moves its account but never overrides its model. No rule for the kind = the old path, no accounts file read.
  - A sub: `subchats::spawn::plan` -> `route::route_sub`. The kind is `route_kind_for_sub`: `build` for a writing sub, `research` for a read-only one, `gate` for a gate. Not a param and not on the brief yet: it switches to `subchats::kind::of_brief` once that module lands. `SubPlan` carries `account_id` (None keeps the main chat's account) and `routing`. A sub placed on another machine (`plan_remote`) skips routing: a rule names this machine's accounts.
  - Scheduled new chats: `route_fired` (kind `new_chat`, or `main_chat` when the item turns the mode on). The item's own picks are explicit, so a rule mostly fills an account left on "default" and clamps.
  - Jarvis is unchanged.
- **Tier interplay.** On a Claude account `resolve_tier` still binds every sub. If the rule (not the main chat) asked for something it refuses (Opus for a writing sub), the sub gets the tier default and the result carries a note; what the main chat itself passed is still refused as before. On an Endpoint account `resolve_tier` does not apply and the rule's model is used as it stands.
- **Spawn result.** When a rule decided something or there is a note, the `spawn_chat` result gains `routing: {kind, account_id, model, effort, source}` and, with notes, `routing_note` (`routing::Applied::attach`).

## Fallback at a limit (pc-1833 phase 3)

Read before editing `routing/limits.rs` or `apply_fallback` in `routing/mod.rs`.

- **Where.** `routing::resolve_with(.., limits)` takes a probe closure; `resolve` is the same with a probe that never reports a limit (tests). The four spawn paths (plain `spawn_chat`/`respawn`, a sub's `plan`, scheduled new chats) pass `routing::limits::prober(state, settings.poll_interval_secs)`. The probe runs only when the rule that decided the account carries a `fallback` (an override with none does not inherit the group's), so a spawn with no fallback reads no usage data.
- **At limit** (`limits::at_limit`, pure over `Signals`): a live rate-limit block in `registry.rate_limit_for_account` with a reset in the future (any account kind); or, for a Claude subscription only, the newest `usage_snapshots` row for the account (`get_snapshots(.., 1, Some(id))`) that is no older than 3 poll intervals, with the 5h window (when the plan has one) or the weekly window at `utilization >= 100` and a reset that is unknown or in the future. A missing, stale or unparsable figure, or a window that already reset, is NOT a limit: never block on unknown. An Endpoint account is read from the provider's own figures instead (see Provider usage), and API-credit accounts are never a rule target, so neither is ever moved by a snapshot. No new polling.
- **Effect.** An explicit account pick is never re-routed. With `fallback: account X` where X exists, is not API-credit, is not the same account and is not itself at limit, the spawn runs on X (the note reads `<label> is at its 5h limit (resets 17:40); using <X label>`). The rule's model is kept when valid on X; an Endpoint X whose model list lacks it takes its own first model, a Claude X goes through the usual validity check. With `wait`, a missing X, an API-credit X, or X also at limit, the spawn stays on the limited account with a note, and that is today's behaviour: the chat is born blocked (`Registry::set_account` stamps the account's window) and the resume/limit strip handles it. No new queue.
- **Notes** ride `Resolved.notes`, so they reach the chat as the spawn result's `routing_note`, like a clamp note. The role sheet's "When the account hits its limit" control (Settings and the project rail share it) has no "coming soon" label.

## Provider usage

Read before editing `daemon/provider_usage/`, `tokens/account_usage.rs`, `routing/limits.rs`'s provider branch or `shared/provider-usage-*.ts`.

- **What.** What an Endpoint account's provider says it has left, shown on the Accounts row, in the Change account picker, the overlay and the header chip's tooltip. Figures only: it never refuses a turn. An unknown figure (no read yet, an error, a stale read) reads "Usage unknown" and is never a limit, never 0%.
- **Daemon module** `daemon/provider_usage/`, built like `daemon::api_credit` (in-memory `ProviderUsageHub`, a 10 minute poller started in `boot.rs`, a debounced turn-end nudge in `pump.rs`, notifier event `provider_usage_changed` with its three registrations: the publish, `daemon_link`'s match arm, `GLOBAL_EVENT_MAP`). Nothing is persisted: the figures come back on the next poll. RPC `get_provider_usage` (phone-readable `P` row) returns `{usage, tokens}`, serves the cache and starts a read in the background for an account that has none (`kick_missing`).
- **Fetchers** (`fetch.rs`, an enum, one per preset, chosen by `Fetcher::for_preset`): DeepSeek `GET /user/balance` (string amounts, `balance_infos`, `is_available`), OpenRouter `GET /api/v1/key` (key cap `limit`/`limit_remaining`, spend day/week/month). Kimi Code and Z.ai/MiniMax have no fetcher yet: both need a real-key probe of the endpoint first (the "Show plan usage" switch belongs with them), and a Custom endpoint never has one.
- **The key** is read from the account's own key file and only ever sent to its own `base_url` host, and only when that host is on the preset's list (`Fetcher::hosts`: `api.deepseek.com`, `openrouter.ai`), over `https`, with no explicit port (`pinned_origin`). An address off the list stores an "unknown" with its reason and makes no call. Redirects are not followed. Every error is passed through `broker::mask::Masker` with the key and never carries the response body. The User-Agent is `ClaudeConductor/<version>`.
- **Tokens counted by Conductor** (`tokens/account_usage.rs`) are the fallback line for every Endpoint account: input, output and cache tokens summed on read from transcripts, for the last 5 hours, today and 7 days. `projects/` is junctioned into every account's config dir, so a directory cannot say whose a transcript is: the session ids that `chat-config.json` binds to the account (`session_ids_for_account`) do. Per-file minute buckets are cached by (mtime, length). The CLI writes one `assistant` line per content block and repeats the `usage` on each, so only the last line of a `message.id` counts. A chat moved to another account (`account_move` keeps the session id) counts wholly under its current account. Usage outside Conductor is not counted, and the row's tooltip says so. Each `get_provider_usage` recomputes the sums off the async threads; the per-file cache keeps a read to the files that grew.
- **Routing.** `limits::at_limit` treats an Endpoint account as at its limit only when a read no older than three poll intervals, with no error, has a window at 100% or more whose reset time is known and still ahead (`Limit.window` `plan`). A balance running out has no reset and so never moves a spawn; only the row says "Out of balance".
- **Frontend.** `shared/provider-usage-format.ts` is the one wording (`providerLine`), `provider-usage-watch.ts` the one live view (`ensureProviderUsageWatch` starts only once an Endpoint account exists), and the Accounts row paints its slot in place (`provider-usage-rows.ts`) so a poll never rebuilds the row's menu. The overlay draws a dial only for an account with a capped window.
- **Tests never call a provider:** mockito only, including the pinning and masking cases.
