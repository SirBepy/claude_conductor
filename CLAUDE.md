# Claude Conductor

Cross-platform Tauri 2 app (Rust + vanilla JS webview). Usage monitoring via cookie-authenticated HTTPS polling of the claude.ai usage API (Chrome/CDP runs only during the one-time login flow to capture the sessionKey), interactive Claude chat sessions (daemon-hosted persistent `claude` per session), and hooks/MCP permission relay.

## Project

Type: other (Tauri 2 / Rust + vanilla JS webview)
Deploy: GitHub Releases; CI builds Windows (NSIS) and Apple Silicon macOS (DMG, restored 2026-08-31). Intel macOS and Linux (DMG / DEB + AppImage) stay paused mid-feature-work, to be restored per dev
`src-tauri/tauri.conf.json`'s committed `version` is intentionally stale locally, CI-owned: `.github/workflows/tauri-release.yml:115-128` jq-rewrites it (and Cargo.toml, package.json) to the real version before every release build.

## Structure

`src-tauri/src/` Rust backend, `src/` frontend SPA, `src-tauri/tauri.conf.json` Tauri config, `android/` a SEPARATE minimal Tauri 2 Android crate (own workspace + lockfile) whose bundled shell just stores a server URL and hands off to the daemon-served SPA

## Commands

- Dev: `cargo tauri dev` (runs from anywhere in the repo; the Tauri CLI auto-locates `src-tauri/tauri.conf.json`)
- Verify: `cargo build --manifest-path src-tauri/Cargo.toml`. **Needs a built `dist/` first on a fresh checkout, or this fails as `RustEmbed` error `../dist does not exist`** - that reads like a broken path, not a missing frontend build. `dist/` is `tauri.conf.json`'s `build.frontendDist` (`../dist`, embedded at compile time) and is gitignored, and `scripts/bootstrap-worktree.ps1` does not produce it. Run `pnpm exec vite build` once first (cheaper than `pnpm run build`, which also reruns the `export_types` cargo test via its `prebuild` script) to unblock `cargo build`/`cargo check`/`cargo test` on `src-tauri`.
- **Frontend unit tests: `pnpm vitest run --poolOptions.threads.maxThreads=5 --poolOptions.threads.minThreads=1`.** Never `--pool=forks --poolOptions.forks.singleFork=true`: cramming every file into one process leaks timers/globals and produces ~15 FALSE failures in files you never touched (`boot-render-gate`, `shortcuts`, `auq-*`, `chat-renderer-edits`), which reproduce on pristine HEAD. The flags above satisfy the concurrency cap without lying.
- Update `vendor/tauri_kit`: `git submodule update --remote vendor/tauri_kit`, then `pnpm tsc --noEmit` to catch breaking kit changes.
- `pnpm run check:css-vars` catches a `var(--name)` reference with no matching declaration anywhere - the silent-fallback bug class swept by hand in 61ba939d and 5ee6dc0c.
- `pnpm run check:view-spec-coverage [files...]` (defaults to `git diff --name-only HEAD`) names every view/wdio spec that depends on a changed source file but was not itself changed - a contract change keeps vitest and tsc green while the spec driving it breaks. Links come from a spec's `await import("/...")`/relative imports, plus a `// asserts: <src path>[, <src path>]` header for specs that only drive the rendered UI (add one when writing such a spec).
- Worktree bootstrap: `powershell -File scripts/bootstrap-worktree.ps1` (run once right after `git worktree add`/`EnterWorktree`, before any build/verify - inits the `vendor/tauri_kit` submodule, runs `pnpm install`, seeds the gitignored `src/types/ipc.generated.ts`, and regenerates `android/`'s gitignored codegen output and NDK cross-compile env if `android/` exists; idempotent, cwd-independent). Not `pwsh`: PowerShell 7 is not installed here. Takes ~9s when it can copy `ipc.generated.ts` from an existing worktree, but several minutes on a fresh clone with no sibling to copy from, since it falls back to `cargo test --test export_types`.

- Android: `cargo tauri android build --target aarch64 --apk` from `android/`, with `ANDROID_HOME`, `NDK_HOME` and `JAVA_HOME` set. **Never invoke `gradlew` directly on a fresh checkout.** Two required build inputs are gitignored and machine-specific, so git alone cannot produce a buildable tree: `gen/android/.../generated/TauriActivity.kt` (codegen output - `MainActivity.kt` extends `TauriActivity` with NO import because it is emitted into the app's own package, so a raw gradle build fails with "Unresolved reference: TauriActivity" and the fix is to run the codegen, NOT to add an import), and `gen/android/tauri.settings.gradle` (hardcodes an absolute path into this machine's cargo registry, pinned to the current tauri version). `scripts/bootstrap-worktree.ps1` now regenerates both automatically (auto-detects `ANDROID_HOME`/`NDK_HOME`/`JAVA_HOME` from their standard install locations, since none of the three are set as persistent env vars on this machine); re-run the script, or `cargo tauri android init` by hand, after a tauri version bump. A release build now fails loud (`gen/android/app/build.gradle.kts`) instead of silently signing with a different identity if `gen/android/keystore.properties` is missing - see `C:\Users\tecno\.android-keystores\README.txt` for the shared key. A third gitignored input, `gen/android/app/google-services.json` (Firebase project `claude-conductor-62582`), is needed by EVERY Android build because the Google Services gradle plugin is applied; CI writes it from the `ANDROID_GOOGLE_SERVICES_JSON_BASE64` secret, and a fresh local checkout gets it by `base64 -d` of that secret's source or a re-download from the Firebase console (Project settings > Your apps).
- **`android/`'s tests run on the HOST target, no NDK needed:** `cargo test --manifest-path android/src-tauri/Cargo.toml` (verified 2026-08-12, todo #620: 8 tests pass, ~2m45s cold / 0.34s warm). It is a separate workspace but shares the global `D:/cargo-target` target-dir with the main crate, so it is release-gated / on-demand, NOT part of the routine per-edit floor - run it manually before an android-touching release, and never concurrently with another cargo command in this repo (shared target-dir lock).
- **Cross-compiling Rust to `aarch64-linux-android` needs four more env vars.** Without them `ring`'s build script cannot find the NDK's clang and the build dies in a C compile, which reads like a broken dependency rather than missing toolchain config: `CC_aarch64_linux_android` and `CXX_aarch64_linux_android` -> `<NDK>/toolchains/llvm/prebuilt/windows-x86_64/bin/aarch64-linux-android28-clang.cmd`, `AR_aarch64_linux_android` -> `llvm-ar.exe` beside it, `CARGO_TARGET_AARCH64_LINUX_ANDROID_LINKER` -> that same clang. The `28` matches `minSdkVersion 28` (read from `android/src-tauri/tauri.conf.json`, not hardcoded). `scripts/bootstrap-worktree.ps1` now writes these into a gitignored `android/.cargo/config.toml` `[env]` block (same pattern as `src-tauri/.cargo/config.toml`'s `RUST_TEST_THREADS`), so a plain `cargo build`/`cargo tauri android build` from `android/` picks them up automatically - re-run the script if the NDK path changes. Verified 2026-08-08 building `android/` with iroh; iroh's defaults select `tls-ring`, not `aws-lc-rs`, so no extra feature juggling is needed.
- **Iteration scripts:** `scripts/build-install-android.ps1 [-Fresh]` wraps the build+`adb install` loop (auto-detects the one connected device, streams output so a stuck Gradle daemon is visible). `scripts/regen-android-icon.ps1 -Scale <f> -MarginRatio <f> [-BackgroundColor <hex>] [-Confirm]` wraps the launcher-icon pipeline documented in `assets/icon/README.md`.
- **Dev daemon serving a phone without bouncing the live app:** build dist, `cargo build --manifest-path src-tauri/Cargo.toml`, then run the daemon binary with `CC_DAEMON_INSTANCE` set (any label) so it binds an ephemeral remote port instead of fighting the production daemon for 27183 - read the actual port from the `remote-access server listening on 127.0.0.1:<port>` log line, or set `CC_REMOTE_PORT` to pin a known one. Point the emulator at `10.0.2.2:<port>`.
- Live-verify against the real app without touching the dev's installed instance: `scripts/live-verify.ps1 up` / `eval <index> <expr>` / `shot <index> <path>` / `down` - isolated debug build, private WebView2 profile, loopback-only CDP on a random ephemeral port, teardown by PID only. Headless by default: the rig runs under server_supervisor docked headless, so neither its windows nor the ones it opens (the Code pop-out) reach Joe's screen or take his focus. `up -Visible` puts it on the desktop instead, and then his typing can land in the rig.
- Phone-path (`isRemote()` true) checks without a device: `scripts/phone-verify.ps1 up` / `status` / `down` runs an isolated daemon from a private copy of `D:\cargo-target\debug\cc-conductor-daemon.exe` (build it first; the script never runs cargo) with a dummy account and a git-initialised scratch project; `e2e/phone/open.mjs`'s `openPhonePage()` returns a logged-in Playwright Pixel 5 page on it. Opening a draft chat and typing in its composer spawns no `claude` process.
- `CC_WHEN_DONE_DRY_RUN` (any non-empty value): the when-done Firing phase runs the full state machine but skips the real sleep/shutdown, logging `when_done: dry-run, would <action>` instead - set it before a live "does when-done actually fire" check so it doesn't sleep/power off the machine.
- View harness port: `playwright.config.ts` serves on 4420 by default; set `VIEW_HARNESS_PORT=<free port>` (e.g. `VIEW_HARNESS_PORT=4431 pnpm exec playwright test <spec>`) so a second concurrent run (parallel builders, two chats) gets its own vite instead of hitting "Port 4420 is already in use".
- One-off component screenshot via `pnpm run test:view`'s browser harness, no throwaway spec: `scripts/harness-shot.ps1 -Driver <ts-file> -Out <png-path>`.
- Show Joe an existing PNG in the in-app preview panel: `scripts/show-shot.ps1 -Path <png-path> [-Title <text>] [-Slug <name>]`.
- Full wdio release-gate sweep in one call (9 free specs with daemon-lifecycle last, then chat-flow/reload-dup on a fake claude, full logs kept on disk, one-line verdict per spec): `scripts/wdio-sweep.ps1` (`-Billed` adds `question-card-live`, and `-Spec question-card-live` is refused without it; `-RealClaude` bills chat-flow/reload-dup too; `-WhatIf` prints the plan without running anything). It re-launches itself under server_supervisor with its whole process tree headless, so the app windows every spec opens stay off Joe's screen, and refuses to run if the supervisor is down; `-Visible` runs it on the desktop. Supervisors older than the `/run` `dock_headless` release can let a window through for a few seconds per spec.

## Rules

- Keep `README.md` in sync when auth flow, tray behavior, scraping approach, or project structure changes. README is user-facing; CLAUDE.md is developer rules only.
- Chat hub is subscription-only, with ONE opt-in exception. `check_metered_billing` in `chat/billing.rs` refuses to spawn if `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`, Bedrock, or Vertex env vars are set. The exception is an `AccountKind::ApiCredit` account (`accounts/api_credit.rs`), which bills the Max plan's monthly API credit. Its chat spawn alone carries `ANTHROPIC_API_KEY`, checked by `check_metered_billing_api_credit`, which still refuses the auth token, Bedrock and Vertex. Every other spawn path (voice, ask, publish, model probe) refuses that account kind. It is never a default, a project binding, or fleet-eligible.
- **API-credit balance needs a Console login, not the claude.ai one.** `daemon/api_credit.rs` polls `platform.claude.com` `/api/organizations/{console_org}/prepaid/credits`, `/spend_limits` and `/current_spend` with the platform.claude.com `sessionKey` (`console-session-<id>.txt`).
  - The claude.ai cookie gets 403 on the Console org, and the Console cookie gets 403 on the Max org (verified live 2026-10-26).
  - `limit_usd` is in cents despite its name.
  - Spending the Max credit counts against the Console spend limit.
  - The cap gate refuses new turns with `API_CREDIT_BLOCKED` (-32007, HTTP 402 on the REST send) when the `subscription_api_credit` tranche hits $0, spend reaches the limit, or a successful credits read shows purchased credit but no Max grant this cycle (purchased credit is never drained by this account kind). Unknown figures never create a block; a non-auth fetch error only keeps a block that was already known.
- **One ask channel: the `ask_user_question` MCP tool. The builtin `AskUserQuestion` is never used.** `--disallowedTools AskUserQuestion` is passed at spawn by `daemon/claude_config/args.rs` (chat sessions), which also get the `PreToolUse` hook safety net (`hooks_server/question.rs`) and the MCP tool itself (`--mcp-config`). The builtin's schema has no `domain`/`badges`, so its cards can never render the chips, and only the MCP path sets `supportsExtras` (the review step's free-text box). Do not re-enable it or add a second ask path.
- Custom IPC commands need only `generate_handler!` registration - no `capabilities/default.json` entry. Capabilities entries ARE required for plugin permissions and new window labels (window labels must match `src-tauri/capabilities/default.json`, e.g. the `session-*` pattern).
- **Any field added to a settings-reachable struct (`Settings`, `ProjectConfig`, `RetentionPolicies`, ...) needs `#[serde(default)]`.** A present-but-incomplete sub-object (the field's key exists but a newer sub-field doesn't) fails deserialization for the WHOLE `settings.json`, not just that field - confirmed data loss, todo 785, Joe lost 7 top-level settings twice on 2026-08-22.
- **Decided 2026-08-08 (todo 521): the STT sidecar is NOT bundled into the installer.** `SttSupervisor::sidecar_dir()` (`src-tauri/src/daemon/stt.rs`) only finds `stt-sidecar/server.py` via an env override, a recorded app-data path, or a directory walk-up from the exe/cwd - none of which hit on an installed app with no repo nearby, so dictation only works from a source checkout today. Bundling a prepared `.venv` would add roughly 2-4GB (`faster-whisper` + `ctranslate2` + CUDA wheels) to the installer for one user; not worth it unless dictation needs to be portable to a machine without the repo.
- **Multi-machine federation module map.** `src-tauri/src/daemon/machines/registry.rs` owns this daemon's identity plus its paired peers, persisted at `<app_data>/machines[suffix].json`. `peer_client.rs` is the HTTP client (`/api/health`, `/api/rpc`, `/api/pair`) for talking to one paired peer. `peer_link.rs` keeps one peer's `mirror.rs` cache entry current over that peer's `/api/global/stream` WS; `hub.rs` owns the set of live `peer_link` tasks, one per peer, resynced on every pairing mutation. `forward.rs` is the RPC-level forwarder for a call whose `session_id`/`id` resolves to a mirrored row; `relay.rs` is its chat-event-stream counterpart. **A second, deliberately separate forwarder lives at `daemon/methods/spawn_chat/forward.rs`** - `machines/forward.rs` keys on a `session_id` already known to be mirrored, while spawn_chat dispatches a brand-new spawn to an explicitly named `machine` argument before any session exists. Do not merge them. `iroh_dial.rs` is `peer_client::reach_url`'s fallback when a peer has no `direct_url`: dials its iroh id and exposes the tunnel as a local loopback proxy port. `peer_scope.rs` enforces each peer's "Can drive chats" switch on `/api/rpc` and the REST send route. Route a session id to a peer only through `machines::mirrored_owner` (local registry first), never `MirrorState::owner_of` directly, or a peer can claim a local chat's id. RPC methods (`list_machines`/`pair_machine`/`unpair_machine`/`set_machine_label`/`list_machine_projects`) live in `daemon/methods/machines.rs`; Tauri wrappers in `ipc/machines.rs`. `MirrorState` also holds a short-lived pending-owner map (`forward_start_session` records a freshly forwarded id so its first attach/send route before the peer's next `instances_changed`) and each peer's pending-prompt cache, refreshed by `peer_link` and merged into `list_pending_prompts` for every caller except a `PeerMachine` one. Clients send `session_id` alongside a prompt's `request_id`/`id` so answers forward. `hidden.rs` owns cross-machine hidden-chat state: the host machine owns a chat's flag, `update_hidden_chats` forwards a mirrored id to its host, and `MirrorState::hidden_sessions` mirrors each peer's list filtered by ownership. Request paths, the 2026-10-08 gap fixes, and known limits: `docs/multi-machine.md`. Frontend: `src/views/sessions/machine-field.ts` is the machine-chip picker in the new-chat project picker (desktop and phone); the Paired machines section (pairing form, peer list, self-label editor) lives in `src/views/settings/subviews/remote-access/remote-access.ts`.
- **`daemon/remote_transport_table.rs`'s `TRANSPORT_TABLE` replaced `SAFE_METHODS`.** It lived in `remote_handlers.rs` until todo 934 split it out; only `allowed` is still re-exported from there, so reach the table and `TransportMask` by their own module path. Each entry's `TransportMask` is `P` (phone only), `PM` (phone and a paired peer machine), or `M` (peer machine only); a method absent from the table is desktop-pipe only, refused for every remote transport. Every row needs a rationale comment, and every `machine: true` mask needs an entry in `allowlist_*`/`peer_machine_mask_is_phone_subset_or_a_named_machine_only_exception` - those tests moved with the table and live in `remote_transport_table.rs`'s own test module. A method that must work for a mirrored session needs to be `PM` or `M`, because `machines/forward.rs` only forwards a method `allowed()` accepts for `Transport::PeerMachine`.
- **`rpc::Transport` replaced the old `REMOTE_TRANSPORT: bool`.** It's `Local` (desktop pipe), `Phone`, or `PeerMachine(machine_id)`. `ConnectionContext::remote` is still `true` only for `Transport::Phone` - never trust a request payload's claimed machine identity, read `ctx.transport` instead (see `methods/machines.rs::peer_unpaired` and `methods/channel.rs::register_channel_rpc`, both of which derive the caller's machine id/label from `ctx.transport`, never from `params`).
- **`Instance.machine: Option<MachineRef>`** means the row is mirrored in from a paired peer (`None` = hosted on this daemon), stamped only by `daemon::machines::all_instances`/`MirrorState::instances`. `is_remote` still means "reached over remote (phone) transport" and the sidebar's "Remote" segment still means an external/automated session kind - none of the three (`machine`, `is_remote`, session kind) implies either of the others.
- **Mirroring loop guards.** `MirrorState::set_instances`/`instances` both drop any row that already carries a `machine` tag, so a peer's own mirrored copy of a THIRD machine is never re-mirrored (no chains past one hop). `machines/forward.rs::forward_one` and `spawn_chat_or_forward`/`post_message_or_forward` never forward when the request's own `ctx.transport`/the resolved peer is `PeerMachine` again - a call already arriving from a peer is always about this daemon's own local sessions.
- **Two daemons on one box for local testing:** `CC_DATA_DIR=<dir> CC_DAEMON_INSTANCE=<label> CC_REMOTE_PORT=<port>` (see `settings/paths.rs::resolve_data_dir`, `daemon/instance.rs`, `remote_server.rs`'s port resolution). Only the default instance (`instance_suffix()` empty) advertises an iroh tunnel (`iroh_tunnel.rs`), so pair two local instances by a direct `http://127.0.0.1:<port>` URL, not iroh. The in-process two-daemon fixture to copy for a new test is `machines/peer_link.rs::tests::two_daemons_mirror_each_other_over_loopback`, built on `remote_server::spawn_on`.
- **People system: the Obsidian vault is the only store.** `src-tauri/src/people.rs` reads `People/*.md` plus client notes (any vault-root note whose frontmatter lists `repos:`; slug = lowercased note name). `daemon/methods/people.rs` serves the one `person` MCP tool (`find`/`remember`, routes `/people/find` and `/people/remember`) and the per-turn "People on <client>" rider; the caller's client comes from its own Conductor project's name/folder matched against `repos:`, never from an argument. `write_draft`'s person gate resolves client-only nicknames through the same lookup. The questionnaire wording lives in the global `/people` skill.
- **Claude's own browser (`src-tauri/src/daemon/browser/`).** A daemon-owned Chrome profile under `<data_dir>/claude-browser/profile`, launched as an ordinary visible window that Joe can minimize (headless trips Google's sign-in checks), driven by one `@playwright/mcp` stdio child per chat, each on its own tab. The `browser_*` tools are Playwright's own schemas from `runtime/tools.json`, listed only when `CC_BROWSER` is set (Settings `claudeBrowserEnabled`, stamped in `mcp_config.rs`), and relayed through `/browser/call`; **each chat drives either this profile or one of Joe's own browsers ("My browser", `browser/target.rs`): the `browser_target` tool (ours, listed beside Playwright's) sets it for one chat from a request like "use my Brave", kept in `ClaudeBrowser.targets` (apart from `sessions`, whose idle sweep would otherwise reset it), and Settings' `claudeBrowserMode`/`claudeBrowserMineApp`/`claudeBrowserMineProfile` only give the starting choice and what "mine" falls back to.** **"Mine" mode goes through our own bridge (`browser/bridge/`, extension source in `browser-extension/` at the repo root, replaced the Playwright MCP Bridge extension and its one-chat-per-profile lock on 2026-10-26).** The extension is a thin `chrome.*` proxy with a pinned manifest `key` (id `bridge::EXTENSION_ID`, pinned by a test); the daemon serves a loopback WS (`/extension`, plus `/cdp/<key>` per Playwright child, both token-gated) and fakes a browser-level CDP session per chat (`bridge/model.rs` holds every routing rule), so stock `@playwright/mcp --cdp-endpoint` drives it. Each chat gets one minimized window, sees only its own tabs, and `Emulation.setFocusEmulationEnabled` is forced on per tab because a minimized (hidden) page skips animation frames and Playwright's click/screenshot then time out (spike 2026-10-26, Chromium 155: every click timed out without it; with it the first of 9 two-chat runs still timed out one screenshot and the next 8 passed). `Page.bringToFront` is mapped to `tabs.update active` and `Browser.close` to closing the chat's window, so nothing raises or closes Joe's browser. Pairing is a native messaging host = this same exe (`main.rs` detects the `chrome-extension://` argv), registered under HKCU for Chrome/Edge/Brave/Chromium by the default instance only (`boot.rs`); it reads `browser-bridge[suffix].json`, so a test browser launched with `CC_DAEMON_INSTANCE` pairs with a test daemon. Chrome rejects `windows.create` bounds less than 50% on-screen, which is why windows are minimized rather than parked off-screen. The entry-point tool note covers both browsers because a chat can switch after the tool list is fixed. Google refuses sign-in in the CDP-launched profile (`chrome.rs` already drops `--enable-automation` and `--headless`, and it still refuses), which is why this mode exists. `browser_run_code_unsafe` is listed only with Settings' `claudeBrowserScriptTool` (stamped as `CC_BROWSER_SCRIPT` in `mcp_config.rs`) and refused by `ClaudeBrowser::call` while it is off. **Bumping `runtime::PINNED_VERSION` means regenerating all three files in `runtime/` together** (`package.json`, `npm-lockfile.json` = the `package-lock.json` from a scratch `npm install --save-exact --ignore-scripts`, renamed because `.gitignore` drops npm lockfiles, and `tools.json` from that version's `tools/list`), after the package safety check. Live check: `cargo test --lib -- --ignored live_browser_end_to_end` (real Chrome, flashes a window on screen for about a second).
- **`pnpm tsc` needs `MachineRef` in `src/types/ipc.generated.ts`.** It's declared in `src-tauri/tests/export_types.rs`; regenerate with `cargo test --manifest-path src-tauri/Cargo.toml --test export_types` after changing `Instance` or any machine-federation type.
