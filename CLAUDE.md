# Claude Conductor

Cross-platform Tauri 2 app (Rust + vanilla JS webview). Usage monitoring via cookie-authenticated HTTPS polling of the claude.ai usage API (Chrome/CDP runs only during the one-time login flow to capture the sessionKey), interactive Claude chat sessions (daemon-hosted persistent `claude` per session), and hooks/MCP permission relay.

## Project

Type: other (Tauri 2 / Rust + vanilla JS webview)
Deploy: GitHub Releases; CI builds Windows (NSIS) and Apple Silicon macOS (DMG, restored 2026-08-31). Intel macOS and Linux (DMG / DEB + AppImage) stay paused mid-feature-work, to be restored per dev
`src-tauri/tauri.conf.json`'s committed `version` is intentionally stale locally, CI-owned: the "Sync version" step in `.github/workflows/desktop-build.yml` jq-rewrites it (and Cargo.toml, package.json) to the real version before every release build, and also sets the CI copy's `beforeBuildCommand` to `npm run build --ignore-scripts` so the release skips the npm `prebuild` hook (a ~10 min debug cargo compile that only writes `ipc.generated.ts`, which the bundle does not read).
**Release shape: Windows publishes first.** `tauri-release.yml` builds Windows and macOS as separate calls of `desktop-build.yml`. `tag` and `publish-windows` wait on the Windows build and `test` only; `publish-macos` adds the macOS assets and its `latest.json` entry afterwards, and `upload-android` attaches the APK. Until `publish-macos` lands, `latest.json` has no `darwin-aarch64` entry and a Mac client's update check ERRORS (tauri-plugin-updater `TargetsNotFound`), it does not report "no update". If macOS fails after Windows shipped, rerun with `gh run rerun <run-id> --failed` within 30 days of the run (GitHub's rerun limit; the artifacts last 90 days but an older run cannot be rerun; the rerun semantics for reusable-workflow jobs are unconfirmed until the first real red macOS run, so check what it reran), never a full rerun or a same-version push: `check` skips once the tag exists, so everything is skipped and macOS never publishes. A code fix for macOS needs a version bump, and until one ships every Mac client keeps getting that update-check error (an "On startup" Mac user only rechecks on launch or Retry). `auto-fix-release.yml` only acts on failures before the tag exists (`check`, `build-windows`, `tag`) for the same reason. `publish-macos` and `upload-android` add assets to an already-published release, so GitHub's "immutable releases" setting must stay off (it is off now).

## Structure

`src-tauri/src/` Rust backend, `src/` frontend SPA, `src-tauri/tauri.conf.json` Tauri config, `android/` a SEPARATE minimal Tauri 2 Android crate (own workspace + lockfile) whose bundled shell just stores a server URL and hands off to the daemon-served SPA

## Rules

- Keep `README.md` in sync when auth flow, tray behavior, scraping approach, or project structure changes. README is user-facing; CLAUDE.md is developer rules only.
- Chat hub is subscription-only, with ONE opt-in exception. `check_metered_billing` in `chat/billing.rs` refuses to spawn if `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`, Bedrock, or Vertex env vars are set. The exception is an `AccountKind::ApiCredit` account (`accounts/api_credit.rs`), which bills the Max plan's monthly API credit. Its chat spawn alone carries `ANTHROPIC_API_KEY`, checked by `check_metered_billing_api_credit`, which still refuses the auth token, Bedrock and Vertex. Every other spawn path (voice, ask, publish, model probe) refuses that account kind. It is never a default, a project binding, or fleet-eligible.
- **API-credit balance needs a Console login, not the claude.ai one.** `daemon/api_credit.rs` polls `platform.claude.com` `/api/organizations/{console_org}/prepaid/credits`, `/spend_limits` and `/current_spend` with the platform.claude.com `sessionKey` (`console-session-<id>.txt`).
  - The claude.ai cookie gets 403 on the Console org, and the Console cookie gets 403 on the Max org (verified live 2026-10-26).
  - `limit_usd` is in cents despite its name.
  - Spending the Max credit counts against the Console spend limit.
  - The cap gate refuses new turns with `API_CREDIT_BLOCKED` (-32007, HTTP 402 on the REST send) when the `subscription_api_credit` tranche hits $0, spend reaches the limit, or a successful credits read shows purchased credit but no Max grant this cycle (purchased credit is never drained by this account kind). Unknown figures never create a block; a non-auth fetch error only keeps a block that was already known.
- **One ask channel: the `ask_user_question` MCP tool. The builtin `AskUserQuestion` is never used.** `--disallowedTools AskUserQuestion` is passed at spawn by `daemon/claude_config/args.rs` (chat sessions), which also get the `PreToolUse` hook safety net (`hooks_server/question.rs`) and the MCP tool itself (`--mcp-config`). The builtin's schema has no `domain`/`badges`, so its cards can never render the chips, and only the MCP path sets `supportsExtras` (the review step's free-text box). Do not re-enable it or add a second ask path.
- **`send_message` requires a `kind`; the caps live in `daemon/hooks_server/messages.rs`.** The 12 kinds, per-kind `text` caps, which kinds take or refuse a `verdict`, and the report-only/correction-only/do_this-only fields are all enforced there (`validate_send`), mirrored in `mcp/tool_schemas_coordination.rs`. A kindless or over-cap call is `ok:false` naming the fix, never a decode error, because a chat spawned before the field existed learns it from that error. The daemon stores nothing about kinds: the chat reads them from the `tool_use` input in the transcript, and derives old-turn shrinking (only the newest turn is full size) from that same transcript, so nothing about it is persisted.
- **A `send_message`/`update_message` the daemon rejects (over its cap, a malformed field) or any `ValidatedJson` request that fails to decode, or an `ok:false` from a handler error on any other relay route (turn status, plan, schedule, drafts, people, jarvis, channel, todos, dashboard card, subchat tool, shared mockup; through `rejected_sends::reply`) draws nothing in the chat.** `daemon/hooks_server/rejected_sends.rs` appends it to `<data_dir>/rejected-sends.jsonl` (rotates to `.old` past 512KB) and `scripts/release-report.ps1` (run by `/release` step 1d through `.claude/release-reports.txt`) groups those shapes since the last `VERSION:` commit, next to the app log's ERROR and WARN lines. The old red "Failed to send" pill per rejection is gone (a model resending until one passes stacked six); a failed row is a hidden `failed-marker` element. Read the report for an ERROR, or a shape with a high count.
- Custom IPC commands need only `generate_handler!` registration - no `capabilities/default.json` entry. Capabilities entries ARE required for plugin permissions and new window labels (window labels must match `src-tauri/capabilities/default.json`, e.g. the `session-*` pattern).
- **Any field added to a settings-reachable struct (`Settings`, `ProjectConfig`, `RetentionPolicies`, ...) needs `#[serde(default)]`.** A present-but-incomplete sub-object (the field's key exists but a newer sub-field doesn't) fails deserialization for the WHOLE `settings.json`, not just that field - confirmed data loss, todo 785, Joe lost 7 top-level settings twice on 2026-08-22.
- **Decided 2026-08-08 (todo 521): the STT sidecar is NOT bundled into the installer.** `SttSupervisor::sidecar_dir()` (`src-tauri/src/daemon/stt.rs`) only finds `stt-sidecar/server.py` via an env override, a recorded app-data path, or a directory walk-up from the exe/cwd - none of which hit on an installed app with no repo nearby, so dictation only works from a source checkout today. Bundling a prepared `.venv` would add roughly 2-4GB (`faster-whisper` + `ctranslate2` + CUDA wheels) to the installer for one user; not worth it unless dictation needs to be portable to a machine without the repo.
- **Multi-machine federation module map.** `src-tauri/src/daemon/machines/registry.rs` owns this daemon's identity plus its paired peers, persisted at `<app_data>/machines[suffix].json`. `peer_client.rs` is the HTTP client (`/api/health`, `/api/rpc`, `/api/pair`) for talking to one paired peer. `peer_link.rs` keeps one peer's `mirror.rs` cache entry current over that peer's `/api/global/stream` WS; `hub.rs` owns the set of live `peer_link` tasks, one per peer, resynced on every pairing mutation. `forward.rs` is the RPC-level forwarder for a call whose `session_id`/`id` resolves to a mirrored row; `relay.rs` is its chat-event-stream counterpart. **A second, deliberately separate forwarder lives at `daemon/methods/spawn_chat/forward.rs`** - `machines/forward.rs` keys on a `session_id` already known to be mirrored, while spawn_chat dispatches a brand-new spawn to an explicitly named `machine` argument before any session exists. Do not merge them. `iroh_dial.rs` is `peer_client::reach_url`'s fallback when a peer has no `direct_url`: dials its iroh id and exposes the tunnel as a local loopback proxy port. `peer_scope.rs` enforces each peer's "Can drive chats" switch on `/api/rpc` and the REST send route. Route a session id to a peer only through `machines::mirrored_owner` (local registry first), never `MirrorState::owner_of` directly, or a peer can claim a local chat's id. RPC methods (`list_machines`/`pair_machine`/`unpair_machine`/`set_machine_label`/`list_machine_projects`) live in `daemon/methods/machines.rs`; Tauri wrappers in `ipc/machines.rs`. `MirrorState` also holds a short-lived pending-owner map (`forward_start_session` records a freshly forwarded id so its first attach/send route before the peer's next `instances_changed`) and each peer's pending-prompt cache, refreshed by `peer_link` and merged into `list_pending_prompts` for every caller except a `PeerMachine` one. Clients send `session_id` alongside a prompt's `request_id`/`id` so answers forward. `hidden.rs` owns cross-machine hidden-chat state: the host machine owns a chat's flag, `update_hidden_chats` forwards a mirrored id to its host, and `MirrorState::hidden_sessions` mirrors each peer's list filtered by ownership. Request paths, the 2026-10-08 gap fixes, and known limits: `docs/multi-machine.md`. Frontend: `src/views/sessions/machine-field.ts` is the machine-chip picker in the new-chat project picker (desktop and phone); the Paired machines section (pairing form, peer list, self-label editor) lives in `src/views/settings/subviews/remote-access/remote-access.ts`.
- **Subchats module map.** A chat with "Use subchats" on (`ChatConfig.subchats_on`) hands jobs Joe names to hidden child chats (subs), whose questions and results show in the main chat's window. Everything daemon-side lives in `src-tauri/src/daemon/subchats/`; add to it rather than spreading logic through lifecycle and hook files. `brief.rs`/`spawn.rs` decide a mode-on `spawn_chat` (required brief, the three tiers, depth 1, cap of 10 started subs (`spawn/cap.rs::started_subs`: a queued sub and a never-started row with no hold hold no slot, since the cap bounds claude processes; the cap is soft: a queued sub that starts later does not re-check it, so a main chat can pass 10 while queued subs start), a duplicate name refused); `held.rs` keeps subs the daemon holds without a child (`after`, the writer queue); `writers.rs` is the one-writer-per-project slot and `worktree.rs` the "Worktree each" alternative (own tree and branch, merged back with a rebase and `merge --ff-only --no-overwrite-ignore`, removed only when merged, clean and with no unpublished submodule commit). `finish.rs`/`turn_end.rs`/`stall.rs`/`stuck.rs`/`ceiling.rs` run a sub's end (`finish_subchat`, the Stop hook's block-nudge-card sequence, the 30-minute and 300-call/3-hour cards; `queue_watch.rs` wakes a main chat once when a sub has waited 5 minutes with nothing in its way (its `after` finished cleanly, the slot is free, or its hold is gone), and `card_watch.rs` wakes it once when a sub's stall card (stuck, stopped, died) has gone 10 minutes without Joe's answer, so a main chat never schedules prompts to poll its subs; `routing.rs` stamps `display_session_id` on question, permission and secret payloads so a sub's card shows in its main chat while `session_id` stays the answer target. `card_log.rs` stores the cards a sub draws in its main chat (`facts.rs` computes their chips from git and the transcript), `back.rs` queues the one line served on Joe's next message, `decisions.rs`/`checkup.rs` keep the decisions log and its checkups, `closing.rs` holds a close that would strand running subs or unmerged worktree commits and moves a family on `respawn` or promotion, `reply.rs` is typing to a sub and "Move to sidebar", `adopt.rs` is the reverse ("Move into main chat" in the chat menu: placeholder brief, an idle child is stopped so the next send relaunches it as a sub, the main chat is woken to hand it a job), `tool.rs` is the `subchat` MCP tool, and `jsonfile.rs` keeps an unreadable state file aside as `.bad` instead of reading it as empty. **The seams:** `subchats::is_sub(&Instance)` is how any list or rule asks "is this a sub" (`subchat_of`, never `worker_of`: a sub must not wake its parent the way a Jarvis worker does); `subchats::on_finished(state, sub_id)` is the one hook a finish fires (card, one line back, decisions, checkup, `after` queue, wake); `cards::raise_card` is the only way the daemon puts its own question card in a window; Frontend: `src/views/sessions/main-chat.ts` (`mainChatInfo`, `showsSubs`: the sidebar row's dots, count, hover and ring), `sub-list.ts` and `subchat-view.ts` (header count, list, reading a sub in place), `src/shared/chat/subchat-cards.ts` and `chat-subchat-card.ts` (cards and chips), `permission-modal/askers.ts` (chips for several askers in one window). - **Chat dashboard (lane 1 of docs/chat-dashboard-design.md).** Settings > Chat defaults > Chat view (`chatView` in settings.json's extra map, absent = Dashboard; the phone always draws Messages) picks what a chat window shows. The model is `src/shared/chat/dashboard/dashboard-model.ts`: pure, it derives every zone from `ChatRenderer.messages` (send_message cards, question cards, `report_turn_status` rows, Joe's own messages) plus `ChatRenderer.dashPlans` (every `write_plan` of the chat, which draws no row; `remapIndices` keeps each plan's `at` and `lastAt` aligned). **To add a card, add a derive function and one entry to `ZONES` there (column, order, derive returning null when empty), then its renderer in `src/views/sessions/chat-dashboard/dashboard-zones.ts`'s `ZONE_VIEWS`, which is typed against `ZoneId` so a zone with no renderer fails typecheck.** Never touch the transcript renderer for a card. `chat-dashboard.ts` mounts beside `.session-messages` from `wireRenderer`, re-derives on `ChatRenderer.onFlushed`, redraws only zones whose HTML changed, and moves the chat's real status line (`.session-thinking`) into the Plan card's status slot while that card is drawn. The transcript keeps rendering underneath, hidden by `.session-pane[data-chat-view="dashboard"]`, so Messages view is byte-for-byte today's. View-harness `mountView` pins `chatView: "messages"` unless a spec passes `chatView: "dashboard"`. **The Answers card is one of two zones with their own DOM** (`chat-dashboard/answers-card.ts`): its zone renders a fixed `.ax-host` and the card draws inside it, so a re-derive never wipes an animation or a thread's message box. Its data is `src/shared/chat/dashboard/answers-model.ts` (only `answer`/`rating` messages count, plus a sub's finish card that carries a `question`: `spawn_chat` and `subchat send` take one, the daemon moves it from the sub's brief onto its next finish card (`finish::commit_finish_at`), and that card is the answer, so a subchats main chat never relays one; `send_message`'s answer-only `question` field is Claude's rewrite of Joe's question, falling back to his message).
